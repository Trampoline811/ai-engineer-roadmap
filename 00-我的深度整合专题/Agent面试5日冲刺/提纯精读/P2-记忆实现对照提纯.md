## 一、概念层 · 记忆 ≠ 知识 ≠ 会话

| 术语 | 含义 | 谁持有 | 典型寿命 |
|------|------|--------|----------|
| **会话记忆**（conversation memory） | 当前 LLM 调用可见的 messages 列表 | LLM 上下文窗口 + harness 的 `messages[]` | 单次会话 |
| **摘要记忆**（summary memory） | 会话历史压成短摘要替进 prompt | harness；`03-memory\03_summary_memory.ipynb` | 单次会话跨多轮 |
| **长期记忆**（long-term memory） | 跨会话持久的事实/偏好/任务产物 | 向量库 / 文件 / DB | 跨会话，理论无限 |
| **技能 / 程序性记忆**（procedural） | "怎么做"的指令（如 SKILL.md） | 文件系统 + frontmatter 索引 | 跨会话，演进 |
| **知识库 / RAG**（区别于记忆） | **领域文档**（产品手册、合同），用户问什么查什么 | 向量库 / BM25 索引 | 文档生命周期 |

**核心直觉**：记忆是「关于你、关于我（Agent）」的**第一人称事实**；知识库是「关于这个世界的**第三人称文档**」。两者的存储和检索很像，但**写入触发完全不同**——记忆由 Agent 行为产生，知识库由人/ETL 注入。

**为什么"会话记忆 ≠ 长期记忆"？** LLM 是无状态的（`99-My idea\AI Agent 学习指南\01.longterm memory.md:39-67`），靠 harness 每次拼 messages 假装"记住"。这只能在同一段会话里生效——新开会话，messages 重新为空。长期记忆要生效必须**独立于会话、跨会话持久**，且每轮可被检索后注入。

**三因子直觉**（Generative Agent 论文）：`03-memory\04_three_factor_scoring.ipynb:25-30` 把每条候选记忆按"与 query 多相关 × 多久前看过 × 写入时多重要"打分。
- **相关性 Relevance**：和当前 query 越像越该出来（向量检索 raw score）；
- **近期性 Recency**：越久未访问越该沉底（`exp(-decay_per_hour × hours)`，默认 0.2/h）；
- **重要性 Importance**：写入时作者给的 0~1 长期权重（"他叫阿明"=0.9，"他最近提过这个工具"=0.5）。

直觉：**加权和**让"很相关 + 刚看过 + 重要"的强事实盖过"很相关但 7 天没动"或"重要但与当前无关"的噪声。

### 概念层两个最常被问的反直觉

1. **"会话里维护 messages 不就是长期记忆吗？"**——不，会话记忆只在该 session 的 messages 列表里，新开会话即清空。LLM 是无状态机（`99-My idea\AI Agent 学习指南\01.longterm memory.md:39-67`），"记住"是 harness 拼 context 模拟出来的。长期记忆必须**独立于会话、跨会话持久**，且每轮可检索——这是 L2 上下文栈的"窗口外"那部分。
2. **"长期记忆 ≠ RAG 知识库"**——记忆是**第一人称**（用户偏好、项目背景、Agent 学到的事），由 Agent 行为产生；知识库是**第三人称**（产品手册、合同、代码库），由人/ETL 注入。两者底层都靠向量检索，但**写入触发、生命周期、策展责任方都不同**。面试官问"记忆和 RAG 区别"时，回答第一句话应该是这两条，而不是"一个是存事实一个是存文档"。

### 📋 面试卡片（概念层）
> "记忆是**关于人/Agent 的第一人称事实**，知识是**第三人称文档**。记忆按三因子打分——相关性 × 近期性 × 重要性——加权融合；会话语境是窗口里的 messages，长期记忆是窗口外的持久 store。新开会话就清空 messages，但不读长期记忆就什么都不记得。**关键反直觉**：(a) 会话记忆不是长期记忆，跨会话必须靠外部 store；(b) 记忆和 RAG 底层检索很像但写入触发与策展责任方完全不同。"

### 3.1 三因子公式与 min-max 批内归一化

**公式**（`03-memory\04_three_factor_scoring.ipynb:131-153`）：

```
recency_raw = exp(-decay_per_hour × hours)            # 单调减，近 0 远 1
rel_n       = minmax(rel_scores)                       # 同批归一化
rec_n       = minmax(recency_raw)                      # 同批归一化
imp_n       = importance                              # 0~1，不再归一化
final       = w_rel·rel_n + w_rec·rec_n + w_imp·imp_n
```
默认 `w_rel=0.5, w_rec=0.3, w_imp=0.2, decay_per_hour=0.2`（1 小时前≈0.819，1 天前≈0.008）。

**为什么 min-max 是批内而非全局**（`04_three_factor_scoring.ipynb:121-128`）：

```python
def norm_minmax(values):
    lo, hi = min(values), max(values)
    if hi - lo < 1e-9: return [1.0 for _ in values]  # 全相等不做区分
    return [(v - lo) / (hi - lo) for v in values]
```

- **量纲对齐**：相关性是向量检索 raw score（不同模型输出 0~1 还是 0~∞ 都可能）；recency 是 `exp(-λ·h)` 已是有界。批内归一化把它们拉到**同一个 0~1 维度**，加权和才有意义。
- **不可用全局分布**：向量库候选数随库规模增长；同一条记忆"上一轮相关分 0.82"在不同批里位次不同，但**只跟"这一批有多像它"竞争**，跟全库分布无关——这正是检索的局部排序语义。
- **极端值吸收**：如果候选里有一条 0.95 远高于其它，min-max 把它压到 1.0、其它等比拉低，**避免被一条神匹配独大**；"全相等"哨兵返回全 1.0，让 `imp` 决定排序，不让"全 0"退化成无信号。

实操：批大小 = 向量检索 topK；"提高近期性权重" 的 demo（`04_three_factor_scoring.ipynb:294-336`）显示 m4 综合分 0.7782 → 0.8429，Top-1 不变（m1 双高）。

**两个常被问的变种**：

- **"为什么 importance 不归一化？"**——`imp` 写入时已 0~1（`add(text, importance=0.9)` 显式给定），再归一化等于把作者主观判断稀释成"批内相对分"，丢掉绝对含义。`imp` 是"这条记忆值多少钱"，`rel_n`/`rec_n` 是"这批里它排第几"——性质不同。
- **"能不能换 EMA 替代 min-max？"**——可以但要付出代价：EMA 给历史平均，跨批可比但**对冷启动不友好**（库小的时候一条命中就拉满），且要保存状态。`minmax` 是**无状态、批内、廉价的占位排序**——召回靠 embedding 而不是打分，所以打分只要"批内相对合理"就够。

### 3.1.x 四层压缩的"看似能合并其实不能"

| 想合并 | 实际不能 | 原因 |
|--------|----------|------|
| L1 snip 与 L2 micro | L1 裁的是**整条消息**（含 assistant 内容），L2 裁的是**消息里的 tool_result 字段** | L1 触发条件是消息数 > 50（结构信号），L2 触发条件是 tool_result 数量 > 3（数据量信号），两者粒度不同 |
| L3 budget 与 L4 LLM summary | L3 是把内容**搬到磁盘**（仍可被工具结果还原），L4 是把内容**生成新摘要**（信息损失） | L3 是无损的、便宜的（0 API），L4 是有损的、贵的（1 API）。混用就把"先试便宜的"原则破掉了 |
| reactive 与 compact | reactive 是**抢救路径**（API 刚返 413），compact 是**预防路径**（token 超阈值） | reactive 必须**激进裁**（只留尾部 5 条），compact 可以**保守**（保头保尾），强行合并 = 平时也只留 5 条，损质量 |

实操红线（`06-harnes\learn-claude-code\s08_context_compact\README.md:185`）：**"顺序不能换"**——L3 必须先于 L2，否则 L2 的占位符把大 tool_result 替换后 L3 落盘时拿到的是占位符而不是原文。CC 源码 `query.ts:379-468` 也是 budget→snip→micro→collapse→auto 这条线。

### 3.2 s08 四层压缩：便宜的先跑贵的后跑

`06-harnes\learn-claude-code\s08_context_compact\code.py:454-477` 的 `agent_loop` 顺序：

```text
L3 tool_result_budget → L1 snip_compact → L2 micro_compact → [token > 50K?]
                                                                   ├ No  → LLM
                                                                   └ Yes → L4 compact_history
                                                                              ↓
                                                                  [prompt_too_long?]
                                                                          ↓
                                                                  L4' reactive_compact
```

- **L1 snip**：消息数 > 50 时保留头 3 + 尾 47，**绝不拆开 `tool_use` 与其 `tool_result` 对**（`s08_context_compact\code.py:294-309`）。教学版 3/47 是简化，CC 真实用 `HISTORY_SNIP` feature gate。
- **L2 micro**：仅保留最近 3 条 `tool_result` 完整内容，其它替换为一行占位（`< 120` 字符不动）。同条 CC 改用 time-based 60 分钟阈值（`README.md:268-278`）。
- **L3 budget**：单条 user 消息所有 `tool_result` 累计 > 200KB → 按大小降序落盘 `.task_outputs/tool-results/<tool_use_id>.txt`，原位置换成 `<persisted-output>Full: <path>Preview: <前 2000 字>`。**预算必须先跑**——L2 占位符一旦替换，L3 就拿不到完整内容了。
- **L4 autoCompact**：阈值用字符数估算（教学），CC 真实用精确 token `contextWindow - maxOutputTokens - 13_000`（`autoCompact.ts:62` AUTOCOMPACT_BUFFER_TOKENS）。LLM 摘要 prompt 必禁工具调用、首尾双重防呆。
- **应急 reactive**：API 仍返 413 才用；只留尾部 5 条原文 + 摘要。**默认 1 次重试上限**。

执行顺序与 CC 源码 `query.ts:379-468` 对齐：budget → snip → micro → collapse → auto。教学版省略 `contextCollapse` 与 `sessionMemoryCompact`（先用 session memory 文件做轻量摘要，不调 LLM）。

### 3.3 hermes provider 生命周期四钩子 + prefetch 位置

`08-hermes-agent\07-mem-provider\hermes_src\agent\memory_provider.py:43-200` 定义 `MemoryProvider` ABC，**4 个 abstract**：`name` / `is_available` / `initialize` / `get_tool_schemas`；**6 个核心（带默认）**：`system_prompt_block` / `prefetch` / `queue_prefetch` / `sync_turn` / `handle_tool_call` / `shutdown`；**9 个可选 `on_*` 钩子**（`on_turn_start` / `on_session_end` / `on_session_switch` / `on_pre_compress` / `on_memory_write` / `on_delegation` 等）。

**Provider 完整生命周期**（综合 `01_provider_abc.md:14-30` + `02_memory_manager.md:5-6` + `03_excerpts_lecture.md:23-35`）：

```text
Session 启动:
  ① add_provider(p)                # Manager 校验：外部只许一个，工具名不 shadow 核心
  ② initialize(session_id, **kwargs)  # 连后端、建资源；is_available 不能打网络
  ③ build_system_prompt()          # 拼 provider 静态块进 SP（frozen snapshot）
每 Turn:
  ④ on_turn_start(turn, msg)       # ★ 在 prefetch 之前；Provider 内部状态清零
  ⑤ prefetch(query)                # ★ 每 turn 同步召回，结果进 TurnContext.ext_prefetch_cache
  ⑥ LLM call (api user += <memory-context>)  # INJECT 围栏进 user，不进 SP
  ⑦ final_response 出来
  ⑧ sync_turn(user, asst)          # ★ 每 turn 异步落库（单 worker 后台）
  ⑨ queue_prefetch(query)          # ★ 暖下一轮的预热
Session 结束:
  ⑩ on_session_end + on_session_switch  # commit_session_boundary_async 绑成一个任务
进程退出:
  ⑪ shutdown_all()                 # drain 最多 5s，再 reverse 调各 provider.shutdown()
```

**为什么 prefetch 放在 turn 前**（`excerpts/01_turn_context.PREFETCH.py:5-19` + `01_provider_abc.md:5`）：

```python
# on_turn_start 先于 prefetch
_turn_msg = original_user_message
agent._memory_manager.on_turn_start(agent._user_turn_count, _turn_msg)
# 然后 prefetch
ext_prefetch_cache = agent._memory_manager.prefetch_all(_query) or ""
```

1. **Provider 需要 turn 边界通知**：`on_turn_start` 清 per-turn 状态、切计数 scope；`prefetch` 才能正确按本轮 query 召回。
2. **用 `original_user_message` 而不是 `user_message`**：`user_message` 可能已注入 skill 正文，会 bloat provider query 甚至搞坏语义（`excerpts/04_run_agent.SYNC_HELPER.py:20-22`）。
3. **prefetch 必须快**（`01_provider_abc.md:138-141`）：契约要求最好返回上一轮 `queue_prefetch` 暖好的缓存；慢 IO 走后台。失败要吞掉（`prefetch:13-19` 整个 try/except）——外部记忆是 best-effort，不能挡对话。
4. **不进 SP，进 user**（`excerpts/02_conversation_loop.INJECT.py:40-54` 注释）：SP 会话内 byte-stable，进 SP 就废 prompt cache。`<memory-context>…</memory-context>` 围栏拼到 `api_msg["content"]` 末尾。
5. **围栏要 sanitize**（`memory_manager.py:152-168`）：`sanitize_context` 剥掉 provider 自己塞的假围栏与 system note；流式输出场景还有 `StreamingContextScrubber` 按 delta 状态机剥跨 chunk 的围栏（防止 `<memory-context>` 在 chunk 边界被切到两半泄露给 UI）。

**写为何异步**（`02_memory_manager.md:208-222`）：历史上 provider 卡网络 ~298s，用户已看到回复但 `run_conversation` 未返回 → CLI/TUI/Gateway 一直显示 running，下条消息触发激进 interrupt。解法：`sync_all` / `queue_prefetch_all` / `commit_session_boundary_async` → `DaemonThreadPoolExecutor(max_workers=1)` → 失败 inline 兜底。

**interrupted 整段跳过**（`excerpts/04_run_agent.SYNC_HELPER.py:24-39`）："Half-formed output is not durable conversational truth"（#15218）。`if interrupted: return` 同时跳过 `sync_all` 和 `queue_prefetch_all`——因为下一条大概率是同一意图的重试，prefetch 拿半截对话召回会污染。

**add_provider 硬规则**（`02_memory_manager.md:80-110`）：
- 外部只许一个；同名 tool 后到者忽略 + warning；
- 核心工具名（`clarify` / `delegate_task`）不可被 shadow；
- `normalize_tool_schema` 防 provider 返回已包好的 OpenAI tool 导致双重 wrap、`function.name` 缺失、整次请求 400（`#47707`）。

### 3.3.x Provider 设计的三个反直觉

1. **`prefetch` 不是 abstract 而是 default-return-`""`**——允许"只读上下文、不写"或"只写不召回"的 provider（`08-hermes-agent\07-mem-provider\hermes_src\agent\memory_provider.py:94-115`）。Manager 扇出时跳过返回空的 provider。如果强制 abstract，每个 provider 都得实现空方法，徒增样板。
2. **`is_available` 禁止打网络**（`01_provider_abc.md:193-197`）——硬规则：返回 False 直接跳过整条外部记忆链路，不挂上。目的：避免"配置错 → 启动卡死"。Provider 应只查 config / 依赖是否安装，**不**实际 ping 后端服务。
3. **`agent_context == "cron"` 时必须 skip 写入**（`memory_provider.py:73-83`）——cron 系统的 system prompt 会污染用户画像（"你是 cron 任务，今天发邮件给 X" 这种上下文写进 user.md 会污染所有未来会话）。这是 hermes 把"subagent 隔离"扩展到 cron 的具体落点。

**4 个 abstract vs 6 个核心的判断标准**（`01_provider_abc.md:53-66`）：abstract = 没有默认实现子类必须 override（`name` / `is_available` / `initialize` / `get_tool_schemas`）；核心 = 有默认实现子类按需 override（`prefetch` / `sync_turn` / `handle_tool_call` / `shutdown` / `system_prompt_block` / `queue_prefetch`）。可写一个新 provider 时，按"先 abstract 后按需 override"顺序填——这就是 `01_provider_abc.md:260-273` 的"实现清单"。

### 3.4 waku 的 gate + consolidation（HERO 1）

`12-hermes-agent-small\waku\memory\retrieval_gate.py:22-54` 整文件就是 HERO #1——**让"该不该检索"本身可学习**：

```text
GATE_PROMPT: 给定用户消息, 决定是否需要长期记忆.
  通用知识/数学/闲聊/自包含请求 → false
  涉及用户生活/人物/计划/历史 → true
  输出 JSON: {"retrieve": bool, "query": str, "reason": str}
```

`should_retrieve` 用 small_model 调一次（~几百 token），返回 `(retrieve?, query, reason)`。**fail open**——如果 gate 自身出错或返回无 JSON，默认 retrieve。**理由**：stale memory 永远好过 lost memory。

**gated_retrieve 串接**（`memory/__init__.py:58-68`）：
1. gate 判 false → return ""（不污染 embedding）；
2. gate 判 true → `facts.search(query, retrieval_top_k)` 拼 `episodes.search(query, top_k=3)` 返回字符串。

`consolidation.py:37-50` 触发条件硬：`len(unconsolidated_rows) < every_n * 2` 直接 return 0。**每 N 条** 才跑一次 LLM 摘要，**不是每 turn**——避免"每条消息都触发抽取"的浪费与噪声。摘要输出 `{"facts":[{"subject","content"}], "episode":"…"}`，写完后 `UPDATE chat_log SET consolidated=1` 标记旧行。

**三柱实现要点**：
- `semantic/store.py:14-19` `_fts_query`：用户文本 → `re.findall(r"[a-zA-Z0-9]{2,}", text.lower())` → `word OR word OR ...`（避开 FTS5 的引号/标点问题）。
- `episodic/store.py:27-38` `search`：`ORDER BY rank, e.happened_at DESC` —— 检索先按 FTS 相关性，并列时**新事件优先**（典型 "上周聊过 X 吗" 场景）。
- `procedural/loader.py:66-90`：扫描 `REPO_SKILLS` + `WAKU_HOME/skills`，**按文件 mtime 算签名**——文件改了自动 reload，不用重启。
- `procedural/installer.py:28-53`：URL → raw URL 转换（GitHub blob 路径、gist 路径）→ 写 `_incoming/SKILL.md` → 调 loader 的 `_parse` 验 frontmatter → 改名到 `<name>/SKILL.md`。

| 怎么选"这轮要不要检索"？ | **gated_retrieve**（HERO #1） | hermes 每 turn 无条件 prefetch | waku 对：慢 IO 不应该常态化，gate 把"是否检索"拆成独立判断 |
| 什么时候 consolidate？ | **每 N 条** | mem0 每 turn 抽、hermes 整 session 抽一次 | 取决于场景：实时性 vs 噪声容忍度 |
| 技能匹配 | **关键词重叠**（`loader.py:83-90`） | 多数用 LLM 路由 | waku 对：可读、可解释、零成本 |

`waku/memory/__init__.py:133-157` 的 `export_markdown` 设计很特别：把 SQLite 里的 facts/episodes 镜像成可读 `MEMORY.md` 文件——"your memory is a file you can open"。这是 waku 对"记忆系统对用户应该可审计"的回答，对中小 AI / 金融科技公司（合规要求高）特别适用。

### 3.5 mem0 三套存储与 ADD-only 抽取（作者详解级）

`99-My idea\AI Agent 学习指南\01.longterm memory.md:160-303` 详解：

| 存储 | 内容 | 写入时机 | 检索时作用 |
|------|------|----------|------------|
| **Main memory**（Qdrant 向量库） | 记忆正文 + 元数据（date/user-agent/hash/lemma/过期/attribution） | `add()` 抽完入库 | ANN 出池（`max(10×4, 60)`） |
| **Entity memory**（第二个 Qdrant collection，**懒加载**） | 实体向量点 + `linked_memory_ids` 链回 Main | 抽完入库时同步抽实体 | **仅给池内记忆加分**（不另出池） |
| **SQLite**（`~/.mem0/history.db`） | 变更日志 + 最近 10 条消息（`session_scope` 分片） | 每次 add 都写 | 给抽取器消代词（"it/he"指谁） |

**三路打分融合**（`01.longterm memory.md:716-823`）：
- 候选池 = ANN `max(10×4, 60)`，**只此一路出池**；
- 池内三路并行：BM25（q 与 memory 都 lemma，sigmoid 映射 0~1，midpoint/steepness 按 query 词数自适应）+ 实体加分（抽实体→embed→实体库搜 top_k=500，4 线程，仅保留 ≥ 0.5，加分 `0.5 × 实体相似度 × memory_count_weight`，链到该实体的记忆越少分越高）；
- 自适应满分 `max_possible`：只有语义 1.0；语义+BM25 2.0；语义+BM25+实体 2.5；语义+实体 1.5；
- `combined = min((语义+BM25+实体)/max_possible, 1.0)`；
- `threshold=0.1` 卡**融合前**的语义分——BM25/实体再高也直接丢（`scoring.py:111`）。

**ADD-only 抽取**（`01.longterm memory.md:478-591`）：
- `infer=true` 走 `ADDITIVE_EXTRACTION_PROMPT`（`mem0/configs/prompts.py` L468-946，**33,699 字符**）；
- system 43 个小节硬规则：只 ADD、要"上下文丰富"、必须穷尽；
- user 模板 7 段：Summary / Last k / Recently Extracted / Existing / New Messages / Observation Date / Current Date + 可选 Custom + Language；
- **OSS 实际填哪些段**：用户摘要=空、Recently Extracted=空（平台版字段）、Existing=top-10、Observation Date=今天（OSS 的 `timestamp` 参数直接抛错，`main.py` L817-818）；
- `parse_messages` 只保留 system/user/assistant 的**文本 content**——assistant 带 `tool_calls` 且无文本的整条丢，`role="tool"` 完全不进抽取。**tool 调用与 tool 结果不参与抽取**（常被写反）。

**实体抽不用 LLM**（`01.longterm memory.md:241`）：`mem0/utils/entity_extraction.py` 用 spaCy `en_core_web_sm` 抽 `PROPER/QUOTED/TOPIC/IDENTIFIER` 四类；spaCy 没装/模型加载失败 → `extract_entities` 返回空列表 → **实体库这条链路静默失效** → 检索退化为"语义 + BM25"。

### 3.5.x mem0 性能优化的三个隐藏选择

1. **ANN 出池量 = `max(10×4, 60)` 而非 `topK`**（`01.longterm memory.md:720`）——池越大重排越好，但太大则 BM25 / 实体打分慢。60 = 经验值，覆盖长尾 + 留余量给语义变体。
2. **threshold 卡在融合前**（`scoring.py:111`）——`if semantic_score < threshold: continue`。**意图**：语义是主信号，BM25/实体只是辅助——辅助再高也救不了"语义不沾边"。这避免了"BM25 假阳性把完全不相关词拉上来"的污染。
3. **hash 比对限定在 top-10 + 本批**（`main.py` L1005-1024）——**意图**：去重是 O(n) 算 hash 碰撞，全库扫描会拖垮每次 add；top-10 是"可能撞"的窗口，本批是"刚加进去还没写过盘"的窗口。**代价**：全库里其它位置的措辞相同的记忆去不到（`mem0/main.py:1005-1024` 显式说明）——这是"性能 vs 严格"取舍，官方选了性能。

**mem0 vs hermes Layer 3 的接口差异**：

| 维度 | mem0（OSS） | hermes Provider（Honcho/Mem0 插件） |
|------|------------|--------------------------------------|
| `sync_turn` 怎么写 | 走 `Memory.add(..., infer=True)` | 走 `MemoryManager.sync_all(user, asst)` 后台队列 |
| 谁做抽取 | 每次都 LLM 抽 | 由 provider 实现（Honcho 是 dialectic reasoning） |
| 谁去重 | mem0 hash + 语义 | provider 自管；hermes Layer1 markdown 是 duplicate = no-op |
| 谁做实体 | mem0 自带 spaCy | provider 自己（Honcho 不抽实体） |
| 跨进程并发 | 走 `Memory.add` 内部锁 | 走 `MemoryManager._sync_executor` 单 worker 池（`02_memory_manager.md:54-77`） |

**一句话**：mem0 把"存+抽+检"做在一个包里，hermes 把"存+抽+检"拆给 provider 各做各的——**前者易用、后者可组合**。

### 3.6 LangGraph checkpoint 的边界

`11-langgraph\02-Agentic-Chatbot-using-LangGraph\backend\graph.py:68-80`：每个节点返回后 LangGraph 内部写 `(thread_id, checkpoint_id, parent_id, state)` 进 SQLite。**对话状态就是 checkpoint**——messages、intermediate state、tools 全在。

`threads.py:4-9`：`get_all_threads()` 用 `checkpoint.list(None)` 拉所有 `thread_id`。**没有"记忆"抽象**——跨 thread 必须自己另搭（如 Store API、向量库）。**适用边界**：thread 内一切自动恢复；thread 间想共享事实必须外接。
> **对比要点**：LangGraph 的 checkpoint = 会话级别"全状态快照"；Hermes 的 Session transcript = 同语义但只存对话；waku 的 state.db = 多表（chat_log/facts/episodes）跨表 join。**只有 waku 在 SQLite 里同时管"事实库 + 历史库"**——这是单用户本地助手的特殊形态。

### 3.6.x 三种"会话边界"的存储范式对比

| 系统 | 会话边界 | 跨会话持久 | 关键文件 / API |
|------|----------|------------|----------------|
| **LangGraph** | `thread_id` | ❌（除非外接 Store） | `SqliteSaver` checkpoint + `get_all_threads()` |
| **pi** | `cwd + timestamp + id` | ✅ 同 cwd 多 session；`/fork` 复制 | `<cwd>/.pi/sessions/--<safe>--/<ts>_<id>.jsonl` |
| **hermes** | `session_id`（Gateway 用 `渠道:provider_session_id:...`） | ✅ Layer1/2/3 跨 session | `~/.hermes/state.db`（FTS5 transcript） + `memory.md`/`user.md` |
| **waku** | `session_id`（用户自定义） | ✅ fact/episode 永久 | `state.db` 三表 + `MEMORY.md` 镜像 |
| **CC 教学 s09** | 无显式 session | ❌（`.memory/` 跟 cwd） | `WORKDIR/.memory/` |

**面试常问**："LangGraph 和 hermes 都能存对话，区别？"——LangGraph 的 checkpoint 是 **graph 执行状态**（节点返回 + 工具结果 + 状态字段），**主要服务"中断恢复"**；hermes 的 transcript 是 **对话流**（user/assistant 文本），**主要服务"按需回查"。一个偏 execution replay，一个偏 audit log**。

### 3.6.x 推荐使用边界

- **LangGraph checkpoint**：图节点多、需要 time-travel debug、需要 human-in-the-loop 审批嵌入到具体节点
- **hermes session transcript**：跨渠道整合（CLI/Telegram/Email 同源）+ 纯文本检索 + 自建 cron
- **pi JSONL**：本地编码项目目录 + 需要 `git`-like 的会话分支
- **waku state.db**：单用户本地助手 + 三柱（事实/事件/技能）+ 可审计 MEMORY.md 镜像

### 3.7 pi 的会话树 + compaction

`13-pi-agent\04-sessions.md:18-22`：cwd 编码目录名 `~/.pi/agent/sessions/--<safe>--/<ts>_<id>.jsonl`。**append-only**（一条 entry 一行 JSON）；header `type=session, version=3, id, cwd, parentSession`；之后每条 entry 有 `id` + `parentId` —— 磁盘上是**行列表，语义是树**。

`/tree` 同文件改 leaf；`/fork` / `/clone` 另开文件（`04-sessions.md:148-191`）。**给 LLM 的是 current leaf→根的 path**（`05-compaction.md:181-206`）：`buildSessionContext` = `buildSessionPath` + `buildContextEntries` → `sessionEntryToContextMessages`。**旧消息还在 JSONL 里**，只是当前 path 走不到——`getTree()` 仍能拼出整棵树。

`compaction`（`05-compaction.md:14-43`）：
- 切点 = 倒着往前加到 `keepRecentTokens≈20K`，**不切在 tool 结果中间**；不得不切在 turn 中间 → 前半轮单独 `TURN_PREFIX_SUMMARIZATION_PROMPT`；
- 有旧摘要 → `UPDATE_SUMMARIZATION_PROMPT`（增量改），无 → `SUMMARIZATION_PROMPT`（从头写）；
- 摘要条目 append 进 JSONL，类型 = `compaction`；下次发给 LLM 时 `convertToLlm` 把 `compactionSummary` 转成 role=user，包进 `<summary>` 标签——**这是换格式不是再压一次**；
- 触发：`_checkCompaction` 在 prompt 前 + `_handlePostAgentRun` 后各一次；区分"已撑爆"和"快满了"——撑爆摘掉失败回复再压再重跑，快满了只压不重跑；
- token 用 `usage.totalTokens || (input + output + cacheRead + cacheWrite)`；旧模型 overflow 不立刻让新模型跟着压。

### 📋 面试卡片（实现层）
> "**三因子 min-max 批内归一化**是为了把量纲不一的向量 raw score 与 `exp(-λh)` 拉到同一 0~1 维度做加权和——全相等时退化为全 1 由 imp 决定排序。**四层压缩**的顺序是 L3 budget → L1 snip → L2 micro → L4 LLM summary，便宜的先跑贵的后跑；L3 必须先跑否则 L2 占位后就拿不到完整内容了。**Provider 四钩子**是 `initialize` / `prefetch` / `sync_turn` / `shutdown`，`prefetch` 放 turn 前是因为要用 `original_user_message` 当 query，且要快、要 fail-open。**waku gate**是'这轮要不要检索'的便宜小模型判断，fail open。**mem0**是 ADD-only + ANN 出池 + 池内三路打分 + 自适应满分。**Checkpoint 不是记忆**——它是对话状态快照，跨 thread 必须外接。"

## 四、工程层 · 拷问式避坑清单

> 每条给"症状 → 错在哪 → 正确做法 → 证据"。

1. **全量回灌 prompt**：把所有聊天历史都拼进 system → 上下文溢出 + 噪声淹没有用信息。正确：摘要替原文（`03-memory\03_summary_memory.ipynb`），或检索 top-k 拼进 user（`03-memory\04_three_factor_scoring.ipynb:283-336`）。证据：`01-windowed_memory.ipynb:96-123` pop 演示。

| 写时机 | 显式 | 每轮 + 整理 | reply 后 / 工具 / 显式 | 每 N 条 | 显式 + 阈值 | 每节点 | 每 turn 后 | 子代理完成 / 主对话 |
| 防投毒 | 无 | 描述去重 | 扫描 + cap + duplicate no-op | 无 | 无 | 内部 | hash 去重 + 语义 | **三道闸**（正则 + 队列 + 分级） |
| 人确认 | 无 | 无 | 工具本身 | 工具本身 | 无 | 无 | 机器去重 | **有**（SUGGESTIONS.jsonl） |

### 5.2 三因子公式（一行背版）

```
recency_raw = exp(-decay_per_hour × hours)         # 0.2/h，1 天前≈0.008
final = 0.5·minmax(rel) + 0.3·minmax(recency) + 0.2·importance
# minmax 是批内归一化，量纲对齐 + 极值吸收
```

### 5.3 Provider 四钩子 + prefetch 位置（一行背版）

```
initialize → build_system_prompt(冻结)            # session 启动
每 turn:  on_turn_start → prefetch → INJECT(围栏进 user)
         sync_turn(异步) → queue_prefetch(暖下轮)
session 结束: on_session_end + on_session_switch 绑成一个任务
进程退出:  drain ≤ 5s + shutdown reverse
```

### 5.4 避坑口诀（背 5 条足矣）

- 动态改 SP = 砸 cache → 进 user 围栏
- interrupted → 整段 skip
- 投毒 → 写前扫描 + cap + 人确认
- LLM 抽 = 慢、spaCy/BM25 抽 = 便宜
- checkpoint ≠ 长期记忆
