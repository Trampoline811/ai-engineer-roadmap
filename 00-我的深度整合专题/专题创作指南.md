### 第一层 · 概念层（400-600行）

**目标**：建立心智模型，回答"是什么"和"为什么"

**核心原则**：
1. **统一类比**：用同一个比喻贯穿多个概念（如"撒网捕鱼"贯穿Recall/Precision）
2. **对比学习**：并排对比相似概念的异同
3. **因果链分析**：用流程图展示概念间的依赖关系
4. **避免公式**：这一层只讲直觉，不讲计算
5. **落到主干实现**：直觉讲完要落到仓库里某一个具体实现上，逐环节给出可在文件里搜到的细节（详见「写作方法」一节的第 2、4 条）

**必备小节**：
- **XX 全景**：四象限/架构图/分类体系
- **核心概念直觉理解**：用类比、表格、对比
- **生产实践**：最小完整框架 + 一个主干实现的逐环节做法 + 按环节看其他实现的替换（写法见「写作方法」第 1、2、3 条）
- **概念间关系**：因果链、互补关系、依赖关系
- **面试卡片**：5-10个快问快答

**写作技巧**：
- ✅ 统一类比法：
  ```markdown
  #### Context Recall & Context Precision — 同一个比喻，两个角度
  
  > **统一类比：撒网捕鱼。**
  > 
  > 池塘里一共有 10 条鱼（GT），你撒了一网捞上来 8 样东西（Retrieved）。
  > 捞上来的东西里——6 条是鱼 ✅，1 只破靴子 🥾，1 把水草 🌿。

  > - **Recall = 6/10 = 0.60** → 还有 4 条鱼漏网了
  > - **Precision = 6/8 = 0.75** → 捞上来的不干净
  ```

- ✅ mermaid 流程图：

      A --> D["❌ 失败模式 3：答非所问"]

- ✅ 对比表格：

**公式演进示例**：
```markdown
### 2.1 Context Recall：三种计算方式对照

#### 版本1：最简Binary版（教学用）

$$Recall = \frac{|GT \cap R|}{|GT|}$$

- 分子：GT和R的交集（命中了多少个真正相关的）
- 分母：GT的总数（一共有多少个相关的）

**示例**：
- GT = {doc1, doc2, doc3} → 3个相关文档
- R = {doc1, doc4, doc5} → 检索返回3个
- 命中 = {doc1} → 只有1个
- Recall = 1/3 = 0.33

---

#### 版本2：考虑排序（Weighted）

$$Recall_{weighted} = \frac{\sum_{i=1}^{|GT|} rel(C_i) \cdot rank\_weight(i)}{|GT|}$$

**为什么要加权？** Binary版把所有GT视为同等重要，
但实际中doc1可能是核心文档，doc3只是辅助信息。

---

#### 版本3：RAGAS实现（含LLM判断）

1. **输入**：`question`, `contexts`, `answer`
2. **LLM提取答案句子**：
   ```python
   sentences = llm.parse(answer)  # ["句子1", "句子2", ...]
   ```
3. **逐句判断可归因性**：
   ```python
   for sent in sentences:
       verdict = llm.judge(sent, contexts)  # 1或0
   ```
4. **计算**：
   $$Recall = \frac{\sum verdict}{len(sentences)}$$

**与Binary版区别**：
- Binary: 文档级匹配（精确但人工标注成本高）
- RAGAS: 句子级+LLM判断（自动但依赖LLM质量）
```

## 🎨 写作风格指南

### 语言风格

#### ✅ 推荐

1. **用真实场景开场**：
   ```markdown
   大多数RAG项目在开发阶段投入了大量精力，
   但到了评估环节却变成了"目测一下答案对不对"。
   ```

2. **用类比解释抽象概念**：
   - "撒网捕鱼"（Recall/Precision）
   - "餐厅点餐"（Faithfulness/Relevancy）
   - "金鱼记忆" vs "持久智能"（Agent Memory）

3. **用对比表格强化理解**：
   | 靠感觉的后果 | 数据驱动的能力 |
   |-------------|---------------|

4. **用 mermaid 图展示流程**：
   ```mermaid
   flowchart LR
       A["检索"] --> R["Recall"]
       B["重排"] --> P["Precision"]
       C["生成"] --> F["Faithfulness"]
   ```

#### ❌ 避免

1. **学术腔**：
   - ❌ "本文将介绍"
   - ✅ "为什么XXX是缺失的一环"

2. **堆砌概念**：
   - ❌ 直接列公式
   - ✅ 先讲直觉 → 再给公式 → 最后代码

3. **单纯罗列**：
   - ❌ "方法1、方法2、方法3..."
   - ✅ "场景A用方法1因为X，场景B用方法2因为Y"

4. **突然出现没解释的行话**（2026-09-18 立规，源自读者实测反馈）：
   - ❌ 正文里突然冒出 `buzzword`、`Separate Checker`、`grace call`、`RCA` —— 读者得停下来猜，或翻到文末附录才明白
   - ✅ **正文第一次出现任何英文行话，一律写成「词（中文）」**，如 `Cron（定时任务）`、`buzzword（行话 / 赶时髦的词）`、`grace call（宽限调用：超预算后允许的最后一次收口调用）`
   - ✅ 同一术语**只注首次**（第二次起不再重复加注，避免啰嗦）；表头、对比表单元格里也一样要注
   - ✅ **附录的中英对照术语表只是兜底，不能替代首次就地加注**——读者是从正文往下读的，不是从附录往回读的
   - ✅ 中文注释控制在 **≤ 22 字**（表格内尤其要短）；完整解释放附录

## 🧭 写作方法（从实战回收）

这一节记录的是"按模板写完之后读者仍然读不懂"的几类问题与对应写法。反例与正例取自 `00-我的深度整合专题\Agent面试5日冲刺\提纯精读\P2-记忆实现对照提纯.md` §1.4 的两版写法。

### 1. 概念层要落一节生产实践

位置在概念澄清之后、因果链之前。谈约束之前，先把真实取值摆出来：谁触发写入、多久一次、检索什么时候发生、按什么阈值淘汰。

- ❌ 直接写"写得太松 → 检索池里全是噪声；淘汰太保守 → store 膨胀"。读者接不住，他还没见过任何真实系统多久写一次。
- ✅ 先给一张触发条件表（一行一个动作，带触发条件与仓库出处），再谈约束怎么从这些节奏里长出来。

### 2. 抽象章节按三步组织：框架 → 主干 → 替换

- ❌ 把仓库里各项目相关的细节平行铺成一张表。信息看着很全，读起来是流水账，读者拿不到"这个系统长什么样"的整体图。
- ✅ 第一步：把系统拆成 N 个环节的完整闭环，画出来，说明缺一个就跑不起来。
- ✅ 第二步：挑仓库里最简单的**完整**实现当主干，逐环节填满，每条给出出处。
- ✅ 第三步：按"被换的环节 / 换成什么 / 换的标准"列其他实现。
- 判据：主干挑"完整"优先于挑"常见"。这一节的目的是先立起认知框架，不是介绍主流方案。

### 3. 组织轴要分开

- ❌ 主干表按系统排，替换表也按系统排。第二张表退化成把第一张的列拉平。
- ✅ 主干表按环节（① 触发写入 / ② 抽取 / ③ 存储 / ④ 检索 / ⑤ 排序与截断 / ⑥ 淘汰），横向对照表按系统。两张表的轴不同，读者才能从两个角度各看一遍。

### 4. 主干实现的描述要细到能核对代码

- ❌ "挂在停止信号上""一次模型调用""有注入预算"——读者无法指着任何一行代码验证。
- ✅ 函数名、模型调用参数（`max_tokens=800`）、阈值（文件数不足 10 直接返回、总量压到 30 条以内、catalog 截到 16000 字符）、注入点（拼进当轮用户消息，不是 system prompt）、触发分支（`stop_reason != "tool_use"`）。
- 判据：一句话里如果没有任何能在文件里搜到的字符串，这句话就是模糊的。

### 5. 教学版与真版分列

仓库里的教学级最小实现与它对应的产品实现经常挨着出现。

- ❌ 把真版才有的能力（注入预算 200 行 / 4096 字节 / 单会话 60KB、异步 prefetch）写成教学版的做法。
- ✅ 同一个环节下分两句：教学版怎么做、真版换成什么。能力属于哪个版本，读的人要能分清。

### 6. 同一事实只写一处

- ❌ 真版 CC 的四层门控既占主干表第 ⑥ 行，又在替换表里单独占一行。
- ✅ 主干表里已经给过的对照，替换表里不再重复；替换表的导语写明"真版对照已随上一张表逐行给出"。

### 7. 方框绘制字符的清查范围含代码文件

- ❌ 只扫 Markdown。`.py` 文档字符串里的 `──` 分隔线同样是 U+2500 系列，扫的时候会被漏掉。
- ✅ 清查覆盖 `00-我的深度整合专题` 下的全部文本文件；分隔线一律用 `--` 或 `-`。

以上第 1 到 6 条靠人工复核，审计脚本查不了"写得清不清楚"。自查办法：把主干表每一行的出处遮住，问自己"照着这句话能不能在文件里定位到"。

## 🔄 创作流程

### Phase 1: 资料收集（1-2小时）

1. **读遍原课程内容**：
   - 所有notebooks
   - README文档
   - 代码实现

2. **提取关键信息**：
   - 核心概念列表
   - 公式/算法
   - 代码片段
   - 典型示例

3. **识别痛点**：
   - 课程中哪些概念理解困难？
   - 哪些地方缺少整体视角？
   - 面试会问什么？

### Phase 2: 结构设计（30分钟）

1. **确定三层划分**：
   - 概念层回答什么问题？
   - 计算层的核心技术点有哪些？
   - 工程层的实践要点是什么？

2. **设计统一类比**：
   - 找一个贯穿全文的比喻
   - 确保类比能解释多个概念

3. **绘制思维导图**：
   ```mermaid
   flowchart LR
       T["主题"] --> C["概念层"]
       T --> K["计算层"]
       T --> E["工程层"]
       C --> C1["全景框架"]
       C --> C2["核心概念1"]
       C --> C3["核心概念2"]
       C --> C4["因果链"]
       K --> K1["技术点1"]
       K --> K2["技术点2"]
       K --> K3["框架汇总"]
       E --> E1["诊断框架"]
       E --> E2["优化策略"]
       E --> E3["避坑清单"]
   ```

### Phase 3: 初稿撰写（3-5小时）

**按顺序写，不要跳跃**：

1. **0. 前言**（30分钟）
   - 痛点场景
   - 对比表格
   - 失败模式图

2. **第一层**（1小时）
   - 全景图/架构图
   - 核心概念（用类比）
   - 因果链分析
   - 面试卡片

3. **第二层**（1.5小时）
   - 符号表 + 阅读指南
   - 每个技术点：公式演进 → 伪代码 → 真实代码
   - 框架汇总
   - 面试卡片

4. **第三层**（1小时）
   - 诊断决策树
   - 优化策略表
   - 避坑清单（至少10条）
   - 面试卡片

5. **附录**（30分钟）
   - 速查表
   - 代码片段
   - 中英对照

### Phase 4: 校对优化（1小时）

1. **结构检查**：
   - 三层是否均衡？（不要某层特别长/短）
   - 递进关系是否清晰？
   - 目录是否完整？

2. **内容检查**：
   - 类比是否一致？
   - 公式是否有误？
   - 代码是否可运行？
   - 表格是否对齐？

3. **面试卡片检查**：
   - 每层至少5-10个问答
   - 覆盖该层所有核心知识点
   - 答案简洁（1-2句话）

4. **最终通读**：
   - 从头到尾读一遍
   - 确保逻辑连贯
   - 删除冗余内容
