## 0. 前言：为什么记忆是 Agent 的"缺失器官"

### "每次对话都是一张白纸"

大语言模型有一个根本性的设计约束：**每次 API 调用都是无状态的**。不管你上一轮跟它聊了什么、三小时前告诉过它什么偏好、上周一起解决了什么问题——下一次 `chat.completions.create()` 调用时，它全部不记得。

这不是 bug，是架构决定的。Transformer 的推理过程不携带跨请求的持久状态。

**没有记忆的 Agent 有三个致命后果：**

```
用户打开 Agent
  │
  ├── ❌ 失败模式 1：对话断裂（遗忘上下文）
  │     └── 第 5 轮忘记了第 1 轮的核心需求，用户被迫重复
  │
  ├── ❌ 失败模式 2：永远新手（无法积累知识）
  │     └── 昨天纠正过的偏好今天又犯，用户觉得"你没在学"
  │
  └── ❌ 失败模式 3：跨会话失忆（每次重开都是陌生人）
        └── 关闭对话窗口 = 清空一切，用户的画像/偏好/历史全部归零
```

> **没有记忆，Agent 就从"持续协作的伙伴"降级为"一次性问答工具"。**

### "靠拼接历史" vs "靠记忆系统"

最简单的"记忆"方案是把历史消息全部拼进 Prompt。这能跑，但有硬天花板：

| 靠拼接历史的后果 | 记忆系统驱动的能力 |
|---|---|
| 窗口满了旧消息直接丢弃——用户 10 轮前提的需求丢了 | **长期记忆**跨会话持久化，用户偏好不会丢 |
| 成本随对话线性增长——第 50 轮和第 1 轮花的 token 一个价 | **摘要记忆**把历史压缩到固定预算，成本可控 |
| 上下文越来越长，模型注意力被稀释（"Lost in the Middle"） | **检索排序**只注入当前问题最相关的记忆 |
| 关闭聊天窗口一切归零——明天用户回来又是陌生人 | **持久化存储**跨会话保留用户画像 |

> **拼接历史是"记事本"，记忆系统是"第二大脑"。前者只负责记，后者负责决定记什么、忘什么、什么时候想起来。**

## 第一层 · 概念层：建立心智模型

### 1.1 Agent 为什么需要记忆

在深入技术细节之前，先建立直觉。问一个问题：**如果一个人的记忆系统瘫痪了，他能正常跟你协作吗？**

不能。他记不住你五分钟前说的话（**短期记忆缺失**），记不住你们昨天做的决策（**长期记忆缺失**），也不会从过去的错误中学到任何东西（**策略记忆缺失**）。

Agent 面临一模一样的问题。LLM 的原生状态只有"当前这一次 API 调用里的上下文"。给它记忆系统，就是给它装上人的三类记忆能力。

**三类能力，三层架构：**

```
人的记忆                          Agent 的记忆
────────                          ────────────
工作记忆（现在在想什么）    →      滑动窗口 / Working Memory
情景记忆（今天发生了什么）  →      摘要记忆 / Episodic Memory
语义记忆（我知道什么事实）  →      长期向量记忆 / Semantic Memory
程序性记忆（我会什么技能）  →      Skills / Procedural Memory
```

> **核心认知：Agent 记忆不是"一个数据库"，而是多层次、多时间尺度的记忆体系——不同记忆解决不同时间跨度和不同信息粒度的问题。**

#### 面试第一问：context window / RAG / memory 三者到底有什么区别？

面试官问"你们的 Agent 记忆是怎么做的"，第一关往往不是问技术细节，而是确认你**分得清三个概念**：

| 概念 | 一句话 | 本质 | 谁在管 |
|------|--------|------|--------|
| **Context Window** | 单次回答能看见的文本，用完即清空 | RAM：快、小、易满 | 模型架构 |
| **RAG** | 从已有文档捞出相应片段塞进窗口 | **读**：图书馆检索（书已放好，只负责找） | 检索系统 |
| **Memory** | 观察交互→判断是否值得存→供未来使用 | **写**：决定什么上架/下架、冲突以谁为准 | 记忆系统 |

> "连续对话的是工具在作弊，把每轮历史重新贴回 prompt，模型才像记得。"——AI_Julie 视频 09

**为什么无状态（stateless）不是 bug？** 同一个模型同时服务千万用户——有人问代码、有人写诗、有人聊家常。如果有状态，这些会话会互相污染。"它要是永远记住的话，那大家的思维就串了。"（AI_Julie 视频 09）无状态让每个会话独立运行，是**产品设计**而非架构缺陷。记住上下文的不是模型本身，是 Agent 这个外层系统——"Agent 套了模型"。

### 1.2 记忆分类体系：从人类记忆到 Agent 记忆

#### 统一类比：人类记忆系统

想象你刚认识一个同事。第一天你跟 TA 开了三次会：

- **工作记忆（Working Memory）**：TA 现在正在跟你讨论的那个方案——"刚才你说的第三点，我补充一下……"——容量极小（约 4±1 个信息块），但实时可用。
- **情景记忆（Episodic Memory）**：TA 记得今天上午的会你坐在窗边、下午的会你换到了角落——带时间戳的事件记录。
- **语义记忆（Semantic Memory）**：TA 一周后记得"你喜欢用中文沟通""你对 React 很熟""你讨厌周五下午开会"——从大量情节中抽象出来的耐久事实。
- **程序性记忆（Procedural Memory）**：TA 知道怎么用 Git、怎么写单元测试、怎么做 code review——自动化的技能。

现在把这个人换成 Agent。Agent 也有完全对应的四层：

```
人类                               Agent
────                              ─────
工作记忆 ≈ 当前对话的滑动窗口       → 短期会话记忆（窗口/Working Memory）
情景记忆 ≈ 今天发生了哪些事          → 摘要记忆 + Episodic 日志
语义记忆 ≈ 我知道关于你的哪些事实    → 长期向量库（偏好/画像/事实）
程序性记忆 ≈ 我会的技能             → Skills.md / AGENTS.md / System Prompt
```

**本节重点讲前三层。第四层程序性记忆本质是"外置知识文件"，在 3.1 节 Write/Read 闭环中展开。**

#### 四象限全景图

```
                 ┌──────────────────┬──────────────────────┐
                 │    时间跨度       │     信息粒度          │
       ┌─────────┼──────────────────┼──────────────────────┤
       │ 短期    │ 滑动窗口记忆      │ Working Memory       │
       │ (本轮)  │ "刚才说了什么"    │ "当前聚焦什么"        │
       ├─────────┼──────────────────┼──────────────────────┤
       │ 中期    │ 摘要记忆          │ Episodic Memory      │
       │ (本会话) │ "这次聊了什么"    │ "今天发生了什么"      │
       ├─────────┼──────────────────┼──────────────────────┤
       │ 长期    │ 向量语义记忆      │ Semantic Memory      │
       │ (跨会话) │ "我知道关于你什么" │ "持久的事实和偏好"    │
       └─────────┴──────────────────┴──────────────────────┘
```

**四类记忆技术速记：**

| 记忆类型 | 中文 | 一句话 | 核心技术 |
|---------|------|--------|---------|
| Windowed Memory | 滑动窗口 | 保留最近 N 条消息，旧的直接丢弃 | Token 计数 + 头部 Pop |
| Summary Memory | 摘要记忆 | LLM 逐步压缩长对话为运行摘要 | 增量 Refine Prompt |
| Long-term Memory | 长期记忆 | 向量库持久化 + 语义检索召回 | Embedding + 余弦相似度 |
| Three-factor Scoring | 三因子排序 | 相关性 + 近期性 + 重要性加权 | Min-max 归一化 + 指数衰减 |

**记忆口诀**：**窗口管"刚说的"、摘要管"这次聊的"、向量管"一直记得的"、三因子里"该先想起来的"。**

### 1.3 记忆间的因果链与互补关系

四类记忆不是替代关系，而是**互补和传导关系**。理解它们之间的因果链，是设计记忆系统的核心。

#### 因果链 ①：滑动窗口溢出 → 触发摘要压缩

> 你每天和同事聊 8 小时。你不可能记住每一个字——你的大脑在**不断压缩**：把"今天早上 TA 说方案 A 行不通因为成本太高，下午又讨论了方案 B……"压缩成"结论是方案 B"。

```
滑动窗口 token 数超过阈值
  → 最旧的消息被 pop 丢弃
    → 如果不做任何处理，早期关键信息永久丢失
      → 摘要在窗口溢出前介入：LLM 压缩旧对话为摘要
        → 窗口释放空间，摘要保留"已发生什么"的语义
```

> **核心认知：滑动窗口和摘要是互补的。窗口管"精度"（保留原话），摘要管"持久"（压缩语义）。不要二选一，叠用。**

#### 因果链 ②：摘要丢失细节 → 需要长期记忆兜底

> 同事记得"你喜欢用中文沟通"——这是从几十次对话中提炼出来的耐久事实。但如果只靠摘要，第一次说"我喜欢中文"可能在第二天就被后面的摘要覆盖了。

```
摘要记忆的文本 buffer
  → 只保留"本次会话的摘要"，跨会话后旧摘要被丢弃
    → 用户画像/偏好/事实需要跨会话保留
      → 长期向量记忆：每个事实独立存储 + 语义检索召回
        → 不管隔了多少天、多少次会话，关键事实始终可召回
```

> **核心认知：摘要管"本会话"的时间线，长期记忆管"跨会话"的耐久事实。前者是流水账，后者是档案库。**

#### 因果链 ③：长期记忆膨胀 → 需要检索排序

> 你认识同事三个月后，关于 TA 的记忆可能有上百条——喜欢的沟通方式、讨厌的会议时间、擅长的技术栈、过去的项目经历……当 TA 问你"帮我看看这个 bug"，你不会把所有关于 TA 的记忆都翻出来，而是**只提取跟编程相关的几条**。

```
向量库中记忆数量持续增长
  → 全量注入上下文会超出窗口且噪声淹没信号
    → 语义检索只召回 top_k 条最相关的
      → 但语义相似 ≠ 当前最需要（可能召回了一周前的相似 query）
        → 三因子打分：不仅看"像不像"（相关性），还看"新不新"（近期性）、"重不重要"（重要性）
```

> **核心认知：语义检索只管"像不像"，三因子打分加上"新不新"和"重不重要"。相关性决定能否被找到，近期性和重要性决定该不该排前面。**

#### 因果链 ④：四类记忆叠加 = 完整记忆系统

```
     本轮对话                  本会话                   跨会话
    ─────────               ─────────                ─────────
    滑动窗口       ──溢出→   摘要记忆                 长期向量记忆
    "刚才说了啥"   压缩     "这次聊了啥"    ──巩固→   "一直记得啥"
        │                      │        门控写入        │
        │                      │                        │
        └──────────────────────┴────────────────────────┘
                                │
                        检索时：三因子排序
                     "该让哪些记忆进入当前上下文？"
```

**一张图总结四条因果链：**

```
短期                          中期                         长期
────                          ────                         ────
窗口溢出 ──────────────→ 摘要压缩 ────────────→ 长期向量持久化
  "记不下了"               "压一压"               "存起来以后查"

长期膨胀 ──────────────→ 三因子排序
  "太多了一条条看不过来"    "挑最该看的几条"
```

> **一句话总结四类记忆的关系：窗口记当下，摘要压历史，向量存事实，排序选精华。**

### 📋 面试卡片：概念层

**Q1：Agent 为什么需要专门的记忆系统？把历史消息拼进 Prompt 不就行了吗？**

A：拼接历史是"记事本"，但不是"记忆系统"。三方面的差距：（1）窗口天花板——拼接受模型上下文限制，满了就得丢弃旧消息，早期关键需求会丢；（2）成本线性增长——第 50 轮和第 1 轮花的 token 一样多，不可持续；（3）跨会话失忆——关闭窗口一切归零。记忆系统解决的是"哪些信息该保留、怎么压缩、什么时候想起来"这一整套决策问题——不只是记录，更是管理。

**Q2：短期记忆和长期记忆到底有什么区别？为什么不能只用一种？**

A：本质区别在时间跨度和信息形态。短期记忆（滑动窗口）是"原话"——精度高但容量极小，超过窗口就丢。长期记忆（向量库）是"语义"——存的是嵌入向量，查询靠语义相似度。短期适合"这一轮对话的连贯性"，长期适合"跨会话的用户画像和偏好积累"。只用短期 → 跨会话失忆。只用长期 → 语义检索不够精确时对话不连贯。两者互补，缺一不可。

**Q3：摘要记忆和滑动窗口都管"短期"，为什么需要两个？**

A：因为它们的"保留方式"完全不同。滑动窗口保留**原话**——精度 100% 但随 token 预算线性丢弃。摘要记忆用 LLM 压缩**语义**——丢失措辞细节但保留核心事实。窗口管"现在这一小段"的精确性，摘要管"过去这一大段"的语义连续性。生产上一个典型的叠用模式是：滑动窗口保留最近 3 轮精确对话，摘要把 3 轮前的内容压缩为一段，两者一起注入 System Prompt。

**Q4：四类记忆之间的关系是什么？是替代关系还是互补关系？**

A：互补关系，且有因果传导。滑动窗口溢出 → 触发摘要压缩（因果链①）。摘要跨会话丢失 → 需要长期向量记忆兜底（因果链②）。长期记忆膨胀 → 需要三因子排序筛选（因果链③）。四类记忆覆盖三个时间跨度：窗口管"本轮"、摘要管"本会话"、向量+排序管"跨会话"。生产上通常是三层叠用——不能指望一类记忆解决所有问题。

**Q5：为什么不把所有对话都存进向量库？还要窗口和摘要干什么？**

A：因为"存"不等于"能用"。存进向量库只解决了持久化问题，但检索精度是瓶颈——语义相似度只能召回"看起来像的"，无法保证召回"刚好需要的"。特别是近期的精确信息（"你刚才说的第三个方案"），语义检索召回率远不如直接把原话放上下文。窗口和摘要的定位是**保证短期连贯性**——它们不用被检索，直接全量注入上下文。向量库只是兜底长期记忆。

**Q6：context window / RAG / memory 三者到底有什么区别？面试官问"你们 Agent 记忆怎么做的"，我第一句该说什么？**

A：第一句先划清边界："我们首先要分清三个东西——context window 是单次能看见的文本、用完即清；RAG 是从已有文档去捞、是读操作；memory 是观察交互后决定存什么、是写操作。"然后讲重点——"我设计的核心不是存什么，而是什么时候写、怎么调和冲突、什么时候该忘。"context window 和 RAG 是已有基础设施，memory 是你要搭建的决策系统。

### 2.1 滑动窗口记忆（短期/会话）

#### 🏫 学习视角

##### 需（Need）：为什么需要滑动窗口

你收到用户的第一条消息"帮我写一个 Python 脚本"。你把消息发给 LLM。LLM 回复了代码。用户说"不对，不要用 requests，用 httpx"。这时如果你不把第一条消息和 LLM 的回复一起发给 LLM，LLM 根本不知道用户说的"不对"是在否定什么。

**滑动窗口解决的就是"当前这一轮对话"的上下文连贯性**——把最近 N 条消息拼接起来，让 LLM 知道之前发生了什么。

##### 根（Root）：为什么需要"窗口"和"丢弃"

消息越多，token 越多。两个约束：
- **成本**：每多 1000 token，API 费用就多一点
- **窗口上限**：每个模型有上下文长度上限（如 128K），超出就报错

所以必须有一个**预算机制**——设定 `max_tokens`，超过就丢弃最旧的消息。

##### 解（Solution）：Token 计数 + 头部 Pop

```
add(role, content)
  → messages.append(新消息)
    → _count_tokens(全部消息) > max_tokens ?
        ├── 是 → pop(0) 丢弃最旧的消息 → 重新计数 → 循环
        └── 否 → 窗口收敛，完成
```

**手算演示：一条消息被挤出的全过程**

假设 `max_tokens = 200`，已有 4 条消息：

| 轮次 | 操作 | 消息列表 | token 数 | 触发 Pop？ |
|:--:|------|----------|:------:|:--------:|
| 1 | system: "你是助手" | [sys] | 8 | 否 |
| 2 | user: "你好" | [sys, u1] | 18 | 否 |
| 3 | assistant: "你好！..." | [sys, u1, a1] | 55 | 否 |
| 4 | user: "解释RAG...(150字)" | [sys, u1, a1, u2] | 210 | ✅ pop(0) 丢掉 system！→ 剩 [u1, a1, u2] = 202 → ✅ pop(0) 丢掉 u1 → 剩 [a1, u2] = 194 |

```
第 4 轮后窗口 = [a1, u2]
丢失的内容：system prompt（"你是助手"）+ 第一轮用户消息（"你好"）
```

> **这个手算暴露了滑动窗口最著名的工程 bug：system prompt 也会被当普通消息挤出窗口。生产实现必须增加"保护位"——system 消息不参与 Pop。**

##### 选（Damage-Choice）：关键参数 trade-off

| 参数 | 作用 | 调大 | 调小 |
|------|------|------|------|
| `max_tokens` | 窗口预算 | 上下文更完整，成本更高，可能超模型上限 | 成本低，但早期关键信息更早丢失 |

**经验值**：`max_tokens` 一般设为模型上下文窗口的 **1/4 ~ 1/3**，为 system prompt 和输出留出余量。

#### 🏭 生产视角

##### 数据从哪来

| 数据字段 | 来源 | 获取方式 |
|---------|------|---------|
| messages | 每轮对话的 user + assistant 消息 | Agent 主循环中的消息列表 |
| max_tokens 配置 | 模型上下文窗口 | 按模型文档设置（GPT-4o=128K, DeepSeek=64K） |

##### 代码实现

```python
from dataclasses import dataclass
from typing import List, Dict
import tiktoken

@dataclass
class ChatMessage:
    role: str   # "system" | "user" | "assistant"
    content: str


class WindowedConversationMemory:
    """Token 滑动窗口：超限则从头部 pop 最旧消息。"""

    def __init__(self, max_tokens: int = 3000):
        self.max_tokens = max_tokens
        self.enc = tiktoken.get_encoding("cl100k_base")
        self.messages: List[ChatMessage] = []

    def add(self, role: str, content: str) -> None:
        self.messages.append(ChatMessage(role=role, content=content))
        self._shrink_to_budget()

    def _count_tokens(self) -> int:
        text = "\n".join(f"{m.role}: {m.content}" for m in self.messages)
        return len(self.enc.encode(text))

    def _shrink_to_budget(self) -> None:
        while self.messages and self._count_tokens() > self.max_tokens:
            dropped = self.messages.pop(0)

    def as_openai_messages(self) -> List[Dict[str, str]]:
        return [{"role": m.role, "content": m.content} for m in self.messages]
```

##### 人工介入点

| 环节 | 频率 | 方法 |
|------|------|------|
| 窗口大小设定 | 初始配置 | 按模型上下文窗口的 1/4~1/3 设定 |
| Token 编码校验 | 模型切换时 | 不同模型用不同 encoding（GPT-4o 用 o200k_base，非 cl100k_base） |
| System prompt 保护 | 每次实现 | 确保 system 消息不参与 Pop 逻辑 |

##### Agent 可执行摘要

> 要实现滑动窗口记忆，你需要：消息列表 + `max_tokens` 预算 + tiktoken 编码器。每次 `add` 后检查 token 总量，超限则从头部 Pop。核心坑：system prompt 默认也被当普通消息挤出，必须加保护位。适合场景：短对话（< 10 轮），早期信息不重要，窗口预算能兜住。

##### 实现变体：按消息条数（Message-count Window）

Token 计数不是唯一路线。滑动窗口有两条实现路径：

| 方式 | 淘汰粒度 | 优点 | 致命缺陷 |
|------|---------|------|---------|
| Token 计数 | 每次 pop 最旧一条，直到总 token 回到预算内 | 精确控制 token 成本 | 回复长度不可控 → 每轮 pop 量不确定 → 窗口最终剩几条无法预期 |
| **消息条数** | 保留最近 N 条（如 10 条），超出直接丢弃 | pop 粒度确定、窗口内容可预期 | 单条消息可能极长（工具返回），token 成本不可控 |

UP主 AI_Julie 明确倾向后者：

> "其實我感覺最合理的一種方式應該是保留多少條消息……比如說 User 算一條、Assistant 算一條，保留最近的 10 條。比這個 TOKEN——這個 TOKEN 的話你真的說不好你的這個回覆會不會太長，導致你每輪都 pop，pop 到最後的 Memory 裡面都快沒東西了。"——AI_Julie 视频 01

**实现要点**：按条数保留时，最好成对保留（User + Assistant 一起丢），而非从单条计数。

**选型建议**：如果模型回复长度可控（你限制了 max_tokens 输出），Token 方式更精确。如果回复长度不可控（含工具调用返回的大段文本），消息条数方式更稳定。生产上可以**两者结合**：按条数保留 + 单条超长时独立截断。

##### ⚠️ 实战踩坑：窗口萎缩与调参两极

**坑 1：回复太长 → 每轮都 Pop → 窗口萎缩到只剩最新两条**

UP主演示时把 `max_tokens` 设为 80，结果每一轮都在 pop：
```
回复长度不可控（没有限长约束）
  → token 快速超限
    → 每轮都 Pop，把早期消息全部冲掉
      → 窗口名存实亡，只剩最新 1-2 条
```
两个修复方向：① System prompt 加"尽量回答简洁在 100 字以内"；② 窗口预算要随实际对话长度校准，不能拍脑袋。

**坑 2：max_tokens 调参的两极失败**

80 太小（每轮都在 pop，"你也感受不到什么"）→ 改 200 又太大（"永远没被丢弃"，窗口形同虚设）→ 改 100 才观察到真实的丢弃过程。**结合真实对话长度校准，是唯一靠谱的方式。**

**调试第一手段**：逐轮打印 memory 状态。"你把 Message 的 History 在每一轮里面都把它打开、打印出来看一下，可能就会更清晰一点，它到底是 pop 掉了个啥。"——AI_Julie 视频 01

### 2.2 长期记忆（向量语义检索）

#### 🏫 学习视角

##### 需（Need）：滑动窗口只能记"刚才"，记不住"以前"

你跟 Agent 说了一百件事——"我喜欢简洁的代码风格""我的项目用 React+TypeScript""不要用 class component"。但如果每次只靠窗口，明天打开新会话，Agent 全部忘光。

**长期记忆解决的是"跨会话"的事实持久化**——把用户偏好、画像、重要事实存下来，后续任何会话都能召回。

##### 根（Root）：为什么要用向量而不是关键词匹配

"我喜欢简洁代码"和"不要写太啰嗦"——关键词完全不重叠，但语义相同。关键词搜索找不到。

向量嵌入把这个语义"方向一致"变成了数学上可计算的余弦相似度。语义相近的文本，向量方向接近，`cos` 接近 1。

##### 解（Solution）：Write 路径 + Read 路径 + LLM 闭环

**Write 路径（写入记忆）**：
```
用户和助手的对话 → LLM 提取可持久化事实 → embed_one(text) → 存入向量库
```

**Read 路径（召回记忆）**：
```
用户新提问 → embed_one(query) → 向量库中逐条算余弦相似度 → 取 top_k → 注入 System Prompt
```

**LLM 闭环（自动从对话中提取记忆）**：
```
每轮对话结束
  → LLM 分析本轮对话，提取"关于用户的、值得长期记住的事实或偏好"
    → 逐条 embed → 写入向量库
      → 下一轮对话时，新提问可语义检索到刚才写入的记忆
```

**手算演示：两条记忆的余弦相似度**

假设归一化嵌入后（cos = dot）：
```
Query: "用户喜欢什么编程风格？"  → 向量 Q = [0.5, 0.3, 0.8]

记忆 1: "用户偏好：代码风格简洁" → 向量 M1 = [0.4, 0.2, 0.9]
  cos(Q, M1) = 0.5×0.4 + 0.3×0.2 + 0.8×0.9 = 0.20 + 0.06 + 0.72 = 0.98  ✅

记忆 2: "用户昨天问了天气"       → 向量 M2 = [0.1, 0.9, 0.1]
  cos(Q, M2) = 0.5×0.1 + 0.3×0.9 + 0.8×0.1 = 0.05 + 0.27 + 0.08 = 0.40  ❌

检索排序：M1 (0.98) > M2 (0.40) → 只取 M1 注入上下文
```

##### 选（Damage-Choice）：存储后端选型

| 后端 | 检索方式 | 优点 | 缺点 | 适用 |
|------|---------|------|------|------|
| 内存 Dict | 暴力遍历 | 零依赖、秒上手 | 不支持大规模 | 教学/Demo |
| FAISS | ANN 索引 | 快、开源 | 需额外依赖 | 中小规模本地部署 |
| Milvus | 分布式 ANN | 大规模生产 | 运维复杂 | 企业级 |
| Qdrant | ANN + 过滤 | Rust 高性能、API 友好 | 社区较小 | 中等规模 |
| pgvector | PostgreSQL 扩展 | 和业务数据共存 | 大规模 ANN 不如专用库 | 已有 PG 的场景 |

#### 🏭 生产视角

##### 数据从哪来

| 数据字段 | 来源 | 获取方式 |
|---------|------|---------|
| 记忆文本 | LLM 从每轮对话中提取 | `llm_extract_memories()` 自动提取 |
| 嵌入向量 | Embedding 模型 | `SentenceTransformer` 或 API |
| 用户画像 | 长期积累 | 同一 user_id 下的所有记忆 |

##### 代码实现（核心）

```python
import hashlib, math, time
from dataclasses import dataclass
from typing import List, Dict, Optional

@dataclass
class MemoryItem:
    id: str
    user_id: str
    text: str
    vector: List[float]
    importance: float       # 0~1，写入时标注
    created_at: float
    last_accessed: float


class SimpleLongTermMemoryStore:
    """内存版长期记忆存储（生产可换 FAISS/Milvus/pgvector）。"""

    def __init__(self, embedder):
        self.embedder = embedder
        self.items: Dict[str, MemoryItem] = {}

    def add(self, user_id: str, text: str, importance: float = 0.5) -> str:
        mem_id = hashlib.md5(
            f"{user_id}:{text}:{time.time()}".encode()
        ).hexdigest()[:12]
        now = time.time()
        vec = self.embedder.embed_one(text)
        self.items[mem_id] = MemoryItem(
            id=mem_id, user_id=user_id, text=text, vector=vec,
            importance=max(0.0, min(1.0, importance)),
            created_at=now, last_accessed=now,
        )
        return mem_id

    def search(self, user_id: str, query: str, top_k: int = 5) -> list:
        q = self.embedder.embed_one(query)
        now = time.time()
        scored = []
        for it in self.items.values():
            if it.user_id != user_id:          # 用户隔离
                continue
            rel = float(np.dot(q, it.vector))  # 归一化后 cos = dot
            age_sec = max(0.0, now - it.last_accessed)
            recency = math.exp(-2e-7 * age_sec)
            score = 0.6 * rel + 0.2 * it.importance + 0.2 * recency
            scored.append((score, it))
        scored.sort(key=lambda x: x[0], reverse=True)
        return scored[:top_k]
```

##### LLM 提取记忆 Prompt

```
分析下面一轮对话，提取关于用户的、值得长期记住的事实或偏好。
每行一条，格式简短，如：用户偏好：沟通风格简洁
若没有可记住的内容，只输出 NONE。

用户：{user_text}
助手：{assistant_text}
```

##### 人工介入点

| 环节 | 频率 | 方法 |
|------|------|------|
| 提取质量抽检 | 每批次抽 5 条 | 检查 LLM 提取的记忆是否合理（不是噪声） |
| 检索结果抽检 | 每周一次 | 验证 top_k 召回的记忆和当前 query 是否相关 |
| 过期记忆清理 | 每月 | 人工审核低质量/过时记忆，删除或标记 |

##### Agent 可执行摘要

> 要实现长期向量记忆，你需要：Embedding 模型 + 向量存储 + LLM 提取 Prompt。Write 路径：LLM 从对话提取事实 → embed → 写库。Read 路径：新 query embed → 语义检索 top_k → 注入 system prompt。核心细节：① 嵌入归一化后余弦=点积（省计算）② 用户隔离（user_id 过滤）③ 增量更新时需重新嵌入。生产级需换 FAISS/Milvus 替代内存 Dict。

### 2.3 摘要记忆（Running Summary）

#### 🏫 学习视角

##### 需（Need）：对话太长，窗口装不下也不想全丢

对话到了第 20 轮，token 已经占用 5000。继续拼全量历史成本太高，但直接丢掉早期消息又怕丢了关键信息。

**摘要记忆就是在"全量保留"和"直接丢弃"之间找一个中间地带——用 LLM 把旧对话压缩成一段摘要，保留语义，丢掉措辞细节。**

##### 根（Root）：为什么不能做一次全局摘要

每轮对话后对全量历史重新摘要 → O(n²) 的 LLM 调用成本。需要**增量更新**——在新摘要基础上只合并"本轮新对话"，不重读全量历史。

##### 解（Solution）：Refine 式增量摘要

```
旧摘要: "用户询问了 Python 脚本的性能优化，助手建议使用异步和缓存。"
  │
  ▼ 本轮新对话
用户："那多线程呢？"
助手："Python 多线程受 GIL 限制，CPU 密集场景推荐多进程。"
  │
  ▼ LLM Prompt: 在旧摘要基础上，合并本轮新对话，输出新摘要
新摘要: "用户询问了 Python 脚本的性能优化，助手建议了异步和缓存。
         后续讨论了多线程的 GIL 限制，推荐 CPU 密集场景使用多进程。"
```

**token 节省实测**（3 轮对话）：
- 完整历史：518 tokens
- 摘要文本：215 tokens
- **节省 303 tokens（约 58%）**

##### 选（Damage-Choice）：摘要 vs 窗口 vs 长期

| 策略 | 旧信息处理 | 优点 | 缺点 | 适合 |
|------|-----------|------|------|------|
| 滑动窗口 | 直接丢弃 | 零额外 LLM 成本 | 早期信息永久丢失 | 短对话 |
| **摘要记忆** | LLM 压缩 | 保留远程语义 | 每轮一次 LLM 调用、丢措辞细节 | 中等长度对话 |
| 长期记忆 | 向量持久化 | 跨会话、语义检索 | 需维护向量库 | 跨会话画像 |

#### 🏭 生产视角

##### Prompt 模板

```

示例
当前摘要：

新对话：

助手：因为它能帮助人类发挥潜能。

示例结束

要求：摘要必须使用中文，保留关键事实，语言简洁。只输出摘要正文，不要解释。

新对话：

```

##### 代码实现

```python
class SummaryMemory:
    """Running Summary：每轮对话后调用 LLM 更新 buffer。"""

    def __init__(self, client, model: str):
        self.client = client
        self.model = model
        self.buffer = ""

    def save_context(self, inputs: dict, outputs: dict) -> None:
        """每轮对话后增量更新摘要。"""
        new_lines = f"用户：{inputs['input']}\n助手：{outputs['output']}"
        prompt = SUMMARY_PROMPT.format(
            summary=self.buffer or "（暂无）",
            new_lines=new_lines,
        )
        resp = self.client.chat.completions.create(
            model=self.model,
            messages=[{"role": "user", "content": prompt}],
            temperature=0,
        )
        self.buffer = (resp.choices[0].message.content or "").strip()

    def load_memory_variables(self) -> dict:
        return {"history": self.buffer}
```

##### Agent 可执行摘要

> 要实现摘要记忆，你需要：一个 LLM（做压缩）+ 增量更新 Prompt + 一个 buffer 字符串。每轮对话后调一次 LLM，用"旧摘要+本轮对话→新摘要"的 Refine 模式。核心优势：token 节省显著（实测省 58%）。核心劣势：每轮多一次 LLM 调用增加延迟和成本；摘要只增不减，极长对话需升级为 Map-Reduce。

### 2.4 三因子打分（检索排序）

#### 🏫 学习视角

##### 需（Need）：语义检索只管"像不像"，但记忆的排序需要更多维度

长期记忆膨胀到上百条后，纯语义检索面临一个问题：一条"一周前用户问过类似问题"的记忆，和一条"一小时前用户刚说过"的记忆，语义相似度可能一样——但后者显然更该被优先注入上下文。

**三因子打分把"该不该优先召回"分解为三个独立信号——相关性、近期性、重要性——各自算分后加权融合。**

> "普通 RAG 的 rank 系统不需要考虑重要性和近期性——文档就在那里，不会过时。但 memory 系统里，记忆会过期、用户会改主意。越近说的话占的比重越高，去年说的话到今年可能已经变了个样了。"——AI_Julie 视频 04

**记忆排序与文档排序的本质差异**：文档是静态的——去年写的技术文档今天仍然正确。记忆是动态的——用户去年说"用 React"，今年可能已经全面迁移到 Vue。这是为什么记忆排序比普通 RAG 排序多两个因子（近期性和重要性）的根本原因。

##### 根（Root）：为什么需要归一化

三个因子的**原始量纲完全不同**：
- 相关性 raw：0.82（余弦相似度，范围 -1~1）
- 近期性 raw：exp(-0.2 × 1h) = 0.819（指数衰减，范围 0~1）
- 重要性：0.9（人工标注，范围 0~1）

直接加权相加 → 量纲差距导致某些因子被"淹没"。必须在**同一批候选内**做 min-max 归一化，把所有因子拉到 [0, 1]。

> "各有各的单位，你怎么比较？没办法比较啊。"——AI_Julie 视频 04

##### 解（Solution）：三步融合

```
Step 1: 每个因子独立算 raw 分
  rel_i   = cos(query_embedding, memory_i_embedding)
  rec_i   = exp(-decay_per_hour × hours_since_last_access)
  imp_i   = memory_i.importance  （已在 0~1）

Step 2: 批内 min-max 归一化
  rel_n = (rel - min(rel)) / (max(rel) - min(rel))  →  [0, 1]
  rec_n = (rec - min(rec)) / (max(rec) - min(rec))  →  [0, 1]
  imp_n 不需要归一化（已在 0~1）

Step 3: 加权融合
  final_i = 0.5 × rel_n_i + 0.3 × rec_n_i + 0.2 × imp_i
```

**手算演示：四条候选记忆**

| 记忆 | 内容 | rel_raw | hours_ago | rec_raw | imp |
|------|------|:------:|:---------:|:------:|:--:|
| m1 | "用户偏好简洁代码" | 0.82 | 1h | 0.819 | 0.9 |
| m2 | "用户问了单元测试" | 0.55 | 24h | 0.008 | 0.6 |
| m3 | "用户过去问过天气" | 0.48 | 168h(7d) | ~0 | 0.5 |
| m4 | "用户刚提到 React" | 0.71 | 0.5h | 0.905 | 0.7 |

**归一化后加权求和（默认权重 0.5/0.3/0.2）：**

| 记忆 | rel_raw | rel_n | rec_raw | rec_n | imp | final | 排名 |
|------|:------:|:----:|:------:|:----:|:--:|:-----:|:--:|
| m1 | 0.82 | 1.00 | 0.819 | 0.905 | 0.9 | **0.952** | 1 |
| m4 | 0.71 | 0.676 | 0.905 | 1.00 | 0.7 | **0.778** | 2 |
| m2 | 0.55 | 0.206 | 0.008 | 0.009 | 0.6 | **0.226** | 3 |
| m3 | 0.48 | 0.00 | ~0 | 0.00 | 0.5 | **0.100** | 4 |

**关键洞察**：m4 的 rel_raw (0.71) 不如 m1 (0.82)，但 m4 更近（0.5h vs 1h）→ rec_n 拉满到 1.0 → 综合冲到第 2。m2 虽然 rel_raw 还有 0.55，但 24h 未访问导致 rec_n 崩塌到 0.009 → 跌到第 3。

##### 选（Damage-Choice）：权重怎么调

| 场景 | 建议权重 (rel/rec/imp) | 原因 |
|------|:------:|------|
| 通用问答 | 0.5/0.3/0.2 | 相关性主导，近期性辅助 |
| 新闻/实时场景 | 0.3/0.5/0.2 | 新鲜度最重要，"昨天的事"可能已经过时 |
| 企业知识库 | 0.4/0.2/0.4 | 长期重要的知识不能因为"最近没访问"就被遗忘 |
| 个性化助手 | 0.3/0.3/0.4 | 用户的稳定偏好（重要性）比"刚说了什么"更该被记住 |

> **权重硬约束**：三个权重之和必须等于 1。权重是在应用中调试出来的，不是定出来的——先跑起来再根据实际效果调整。"你可以根据你的实际的应用来调节权重，使你的这个 rank 的效果更好。"——AI_Julie 视频 04

#### 🏭 生产视角

##### 数据从哪来

| 数据字段 | 来源 | 获取方式 |
|---------|------|---------|
| rel_scores | 向量检索 | embedding 模型计算 query 和每条记忆的余弦相似度 |
| last_access_ts | 存储层的访问时间戳 | 每次 search 命中时更新 |
| importance | LLM 提取时标注 | 提取 Prompt 中要求 LLM 评估重要性 (0~1) |

##### 代码实现

```python
import math, time
import numpy as np

def norm_minmax(values):
    """Min-max 归一化到 [0, 1]。全相等时返回 1.0。"""
    lo, hi = min(values), max(values)
    if hi - lo < 1e-9:
        return [1.0] * len(values)
    return [(v - lo) / (hi - lo) for v in values]


def rank_memories(rel_scores, memories,
                  w_rel=0.5, w_rec=0.3, w_imp=0.2,
                  decay_per_hour=0.2):
    """三因子加权排序。返回 (综合分, 记忆, 因子明细) 列表。"""
    now = time.time()
    recency_raw = [
        math.exp(-decay_per_hour * max(0.0, (now - m.last_access_ts) / 3600.0))
        for m in memories
    ]
    rel_n = norm_minmax(rel_scores)
    rec_n = norm_minmax(recency_raw)

    ranked = []
    for i, m in enumerate(memories):
        final = w_rel * rel_n[i] + w_rec * rec_n[i] + w_imp * m.importance
        ranked.append((final, m, {
            "rel_raw": rel_scores[i], "rel_n": rel_n[i],
            "rec_raw": recency_raw[i], "rec_n": rec_n[i],
            "imp": m.importance, "final": final,
        }))
    ranked.sort(key=lambda x: x[0], reverse=True)
    return ranked
```

##### Agent 可执行摘要

> 三因子打分是纯算法，不调用 LLM。输入：语义检索的 raw 相关性分 + 每条记忆的 last_access_ts + importance。三步：各因子独立算 raw → 批内 min-max 归一化（边界处理：全相等返回 1.0） → 加权求和排序。核心参数：`decay_per_hour` 默认 0.2（1h 后 rec≈0.82，24h 后≈0.008），权重默认 0.5/0.3/0.2，按场景调整。源自 Generative Agent 论文。

##### ⚠️ 框架内置记忆的隐藏坑：LangChain 的内置 System Prompt

> "LangChain 它里面很多系统的 PROMPT 是默认的写好的，所以有的时候会不打你的预期。为什么不打你的预期？就是因为它有一些 SYSTEM PROMPT 它内置了。"——AI_Julie 视频 01

### 📋 面试卡片：计算层

**Q1：滑动窗口的 token 计数用的是什么编码？为什么不能用简单的 len()？**

A：用 tiktoken 库的模型对应编码。不能用 Python 的 `len()` 因为 LLM 的 token 不是字符——一个中文字可能占 2-3 个 token，一个英文单词可能占 1-2 个 token。token 是 LLM 实际消耗的计算单元，用字符数计数会导致"你以为没超限，实际已经超了"。不同模型用不同编码（GPT-4o 用 o200k_base，DeepSeek 有自己的 tokenizer），模型切换时要同步换编码。

**Q2：长期记忆搜索中，为什么嵌入归一化后余弦相似度等于点积？**

A：余弦相似度公式 `cos(A,B) = A·B / (|A| × |B|)`。当两个向量都经过 L2 归一化后，它们的模长 `|A| = |B| = 1`，分母变成 `1×1 = 1`，所以 `cos = A·B`（点积）。直接用 `np.dot` 省掉除法操作。在 SentenceTransformer 中设置 `normalize_embeddings=True` 即可。

**Q3：Running Summary 和 Map-Reduce Summary 有什么区别？什么时候升级？**

A：Running Summary 是 Refine 式增量更新——每次在旧摘要基础上合并新对话，O(n) 的 LLM 调用次数。Map-Reduce 是分块摘要——先对每段独立摘要，再合并摘要的摘要，适合历史极长（几百轮）的场景。升级信号：当 Running Summary 的 buffer 越来越大、单次增量更新耗时明显增加时，切换为 Map-Reduce。

**Q4：三因子打分里的 min-max 归一化为什么要"批内"做，不能全局做吗？**

A：因为 min-max 是相对排序，不是绝对分数。全局归一化需要存储历史上所有分数的 min/max，这在高频检索场景中不可行（每时每刻都在变）。批内归一化在每次检索时对当次召回的候选集做归一化，保证"相对排序"正确即可。边界处理：当批内所有候选分数相同时返回全 1.0（不做区分）。

**Q5：为什么三因子里的近期性用 exp(-decay × hours) 而不是简单的 "1/hours"？**

A：指数衰减有两个数学特性天然适合近期性建模：① 在 [0,1] 有界（1/hours 在 hours→0 时爆炸）；② 衰减速度可控——调 decay 参数即可改变"忘得多快"。decay=0.2 时，1h 后≈0.82，24h 后≈0.008，7d 后≈0——这种"近期快速衰减、远期趋于零"的行为是线性衰减做不到的。

**Q6：滑动窗口、摘要、长期记忆能叠用吗？怎么组合？**

A：可以且应该叠用。典型组合：滑动窗口保留最近 3 轮精确原话 + 摘要把 3 轮前的内容压缩为一段 + 长期向量记忆管跨会话偏好/事实。三者一起注入 System Prompt。窗口管"精度"，摘要管"连贯性"，向量管"持久性"。优先级：窗口 > 三因子排序后的长期记忆 > 摘要。

**Q7：长期记忆搜索中的用户隔离为什么重要？怎么实现？**

A：多用户场景下，用户 A 的记忆不应被用户 B 的 query 召回——隐私和准确性双重要求。实现就是 `search` 中加 `if item.user_id != target_user_id: continue` 过滤。这也是为什么每条 MemoryItem 必须带 `user_id` 字段。如果用 FAISS/Milvus，需要在索引中加 user_id 元数据，检索时做 post-filter。

**Q8：什么时候该用框架内置记忆（AutoGen ListMemory），什么时候该自建？**

A：AutoGen ListMemory 就是内存列表 append——没有持久化、没有检索、没有排序。适合 Demo 阶段快速验证"记忆"概念。以下任一信号出现就该自建：①需要跨会话持久化 ②记忆数量超过 10 条（语义检索需求）③需要多维度排序（三因子）④多用户隔离。自建的最小可行实现 = Embedding + Dict + 余弦相似度。

**Q9：摘要记忆的 Prompt 为什么用增量更新（Refine）而不是每次从头总结全量历史？**

A：从头总结全量历史 = 每轮对话都要把整个历史发给 LLM → 成本 O(n²)，n 轮后不可接受。增量 Refine 每次只发"旧摘要 + 本轮新对话"，输入 token 数恒定，O(1) 的 LLM 输入成本。代价是错误会累积——如果旧摘要丢了关键信息，后面摘要永久丢失这个信息。这是"省成本"和"保精度"之间的经典 trade-off。

**Q10：三因子打分的 decay_per_hour 默认 0.2，这个值怎么来的？能调吗？**

A：0.2 是经验值——1h 后 rec≈0.82 意味着"一小时前的记忆还有八成新鲜度"，24h 后≈0.008 意味着"昨天的记忆在新 query 面前几乎不考虑"。这是 Generative Agent 论文中的默认参数。调整原则：新闻/实时场景上调到 0.5（更快遗忘），企业知识库下调到 0.05（更慢遗忘），个性化助手上调到 0.3（更偏近期）。调参前先问自己"用户期望多久前的信息还应该被记住？"

**Q11：滑动窗口用 Token 计数好还是按消息条数好？**

A：取决于回复长度是否可控。Token 方式精确控制成本但怕"一条回复超长冲掉所有历史"；消息条数方式 pop 粒度确定、窗口内容可预期，但怕"单条消息极长（工具返回）"。产上可以两者结合：按条数保留 + 单条超长时独立截断。核心不是选哪个，而是理解各自的失效模式——面试时能说出两种方式的 trade-off 和各自在什么场景下会崩，比说"我都用 Token"高一个档次。

**Q12：三因子排序和普通 RAG 排序有什么区别？为什么 memory 要比 RAG 多两个因子？**

A：本质区别在于排序对象的生命周期。RAG 的排序对象是静态文档——去年的技术文档今年仍然正确，你只需要关心"像不像"（相关性）。Memory 的排序对象是动态记忆——用户去年的偏好今年可能已经变了（"去年用 React，今年用 Vue"），你不仅要管"像不像"，还要管"新不新"（近期性）和"重不重要"（重要性）。一句话：文档不会过时，记忆会。

## 第三层 · 工程层：持久化、诊断与生产化

### 3.1 Write/Read/Reconcile/Forget 闭环

前两章讲的四类记忆都是"存"和"取"——讲的是技术实现。但记忆系统真正难的不是怎么存，而是**决定存什么、怎么让记忆自洽、什么时候该忘**。

#### 记忆不是"套了马甲的数据库"

把记忆当成数据库来用（"用户说一句就存一行"）会出现三个问题：
- **噪声积累**：大多数对话内容是废话（闲聊、失败的中间步骤、LLM 的推测）——存进去污染检索
- **事实冲突**：用户周一说了"用 React"，周三说了"用 Vue"——两条矛盾记忆并排躺在库里，检索随机召回一条
- **永远不会忘**：数据库只增不减，旧的、过时的、被推翻的记忆永远占据检索名额

#### 记忆闭环的六个环节

```
Write → Store → Reconcile → Retrieve → Rank → Forget
  │       │         │           │         │        │
  │       │         │           │         │        └── 有意遗忘：TTL 过期、
  │       │         │           │         │            冲突后标记旧值失效、
  │       │         │           │         │            长期未访问自动清理
  │       │         │           │         │
  │       │         │           │         └── 排序：三因子/LLM 选择
  │       │         │           │              "哪些该注入当前上下文"
  │       │         │           │
  │       │         │           └── 检索：语义 / SQL / 关键词
  │       │         │                "挑出跟当前 query 有关的"
  │       │         │
  │       │         └── Reconcile（调和）：新旧记忆冲突时
  │       │              更新/覆盖/标记过时，不让矛盾记忆并存
  │       │
  │       └── 存储：文件 / 向量库 / SQL / 内存
  │
  └── Write 写入：每轮结束后回看对话，
      只留耐久事实（偏好/决策/事实），丢掉噪声
```

> **核心认知：好的 Memory 系统不靠"记得更多"，而靠"故意忘掉什么"。控制器（决定保留/丢弃/覆盖）比底层存储更重要。**

#### Reconcile 五种冲突策略

当新记忆和旧记忆矛盾时，怎么处理？不是简单的"删旧写新"——取决于风险等级：

| 策略 | 做法 | 适合场景 |
|------|------|---------|
| **A. Last-Write-Wins** | 同 key 直接用新值覆盖 | 偏好、当前目标、阻塞点（默认首选） |
| **B. 版本化+失效标记** | 不物理删，标记 `status=stale`，检索只取 active | 需要审计回放的场景 |
| **C. Merge 合并** | 互补非互斥 → 合成一条 | 可并存的偏好/禁止项 |
| **D. 冲突升级** | 都像真又互斥 → 问用户或 Reflector 按置信度裁决 | 高风险事实 |
| **E. 时间窗/TTL** | 临时状态设过期自动 Forget | "这周在赶 auth 项目"类短期事实 |

> **面试口述**："记忆系统不是存了就行，最难的工作是调和——当用户周一说了 A、周三说了非A，你要决定信哪一个。Last-Write-Wins 是最简单的默认策略，关键冲突要升级给用户确认。"

**Reconcile 的隐含前提：键值对齐**。五种策略生效的前提是——同一个 key 只允许一条有效记忆。"每个检索 key 对你都只能是同一条信息，不是多条。"（AI_Julie 视频 09）如果同一个偏好存了多条，检索时两条都捞出来，模型不知道该听谁的——这不是模型幻觉，是你自己的存储设计导致的。

**检索侧的降级处理**：conflict 标记的记忆在检索时降权或不注入。"这种 conflict 的还是不注入为好，注入了反而让模型产生幻觉。"（AI_Julie 视频 09）已有报告五种冲突策略表覆盖了**存储侧**处理（写的时候怎么办），本补充覆盖了**检索侧**处理（读的时候遇到冲突怎么办）——两边配合才完整。

#### 一轮对话的时序：开场先读，收尾再写

```
读路径（开场）：
  retrieve（按 query + key 捞候选）
    → 过滤 stale / conflict / 过期 TTL
      → rank 精排只留最好的几条
        → 拼装 context = system + 精炼记忆 + 近期对话（窗口）
          → "不是整个倒进 context"（AI_Julie 视频 09）

写路径（收尾）：
  回看本轮一问一答
    → 有无耐久事实？
      ├── 无 → 直接 forget 丢掉，不进库
      └── 有 → store 候选事实
            → reconcile 判断：无旧直接写入 / 互斥覆盖 / 互补 merge / 不确定标 conflict
              → 门控优化："不是每一轮对话结束都去做一遍，而是搞了个十轮或者 token 超过了 2000 再去做"（AI_Julie 视频 09）
```

#### Working Memory 的更新：字段替换，不许叠加

Working Memory 存的是"绝对不能丢失的信息"（核心目标、硬性偏好、禁止项、身份约束）。更新时必须是**字段级替换**，不能叠加：

> "靠 update working memory 在对话中实现实时的更新——是直接替换特定字段，而不是覆盖的叠加，让模型产生了幻觉。昨天的人设跟今天的人设不一样，昨天的人设没删，模型不知道你到底是哪个人设。"——AI_Julie 视频 08

因果链：旧人设+新人设并存 → 模型看到两个矛盾的身份 → 随机选择一个 → 幻觉是你导致的，不是模型的问题。

#### Agent Tool Loop 设计模式

Harness 工程的核心原则——"你只要学会了这个逻辑，用哪个框架都可以"（AI_Julie 视频 06）：

```
┌─────────────────────────────────────────────┐
│  Tool Loop 三原则                             │
│                                              │
│  1. 必须设 max_steps                          │
│     "你不能让 tool loop 一直不断执行，         │
│      然后消耗 n 多 token，最后也没有成功"       │
│                                              │
│  2. 失败就是结局，显式返回失败                  │
│     任务到此为止，不要无限重试                  │
│                                              │
│  3. human in the loop 兜底                    │
│     失败后人类决定改 prompt 重新来              │
│     "我觉得还蛮合理的"                         │
└─────────────────────────────────────────────┘
```

**三维评估体系**（补充 3.6 记忆评测）：
- 完成度：LLM-as-judge 判断任务是否完成（注意：agent 自报"完成了"不可信，必须有 trace 做判断依据）
- Token 成本：每轮对话花了多少 token、多少钱（"你可以告诉你的用户客户说你这东西到底要花多少钱"）
- Latency：延迟、错误率

评估后闭环：设标准 → 不达标 → 回溯优化 memory 系统和 loop。目前业界"大家还停留在第一步——把它跑通，评估这一步也正在优化中"。

#### Claude Code 的真实实现（可作为工程范本）

Claude Code 的记忆系统是"文件仓库 + 索引 + 按需加载"模式的成熟实现：

**存储结构**：
```
~/.claude/projects/<project>/memory/
  ├── MEMORY.md          ← 索引文件（常驻 SYSTEM，被 prompt cache 缓存）
  ├── <记忆1>.md         ← 独立 topic files（按需加载）
  ├── <记忆2>.md
  └── ...
```

**四条工程不变量**：

1. **两步保存（Two-step save）**：先写完整 topic file → 再在 MEMORY.md 索引中追加一行指针。两步间崩溃最坏结果是孤儿 topic file（不丢数据），索引保持一致。

2. **索引有界常驻，文件按需加载**：MEMORY.md 硬上限 ~200 行/25KB（常驻 SYSTEM，可被 Cache）。topic files 无限细节但只在需要时加载（不破坏 cache）。

3. **LLM side-query 选记忆（不是 embedding！）**：`select_relevant_memories()` 把近期对话 + 所有记忆的 name+description 发给 LLM 做轻量 side-query，选相关文件名（最多 5 条）。失败降级到关键词匹配。**这跟向量检索是两条完全不同的路——向量靠数学、LLM side-query 靠理解。**

4. **本地覆盖优先（Local overrides win — always）**：`Organization-wide → User-level → Project-level → Local override`，逐级收窄，最本地指令最终说了算。

#### 与数据库方案对比

| 维度 | 文件仓库 + 索引 | 数据库方案 |
|------|:------------:|:--------:|
| 简单性 | 极高（Markdown 文件） | 需要部署和维护 |
| 查询能力 | 弱（靠索引行 + LLM 选择） | 强（SQL/向量检索） |
| 版本控制 | ✅ git 天然支持 | ❌ 需额外设计 |
| 人类可读 | ✅ 直接打开看 | ❌ 需要查询工具 |
| 适合规模 | < 200 条记忆 | > 200 条记忆 |

> **实践建议**：对大多数个人 Agent，文件方案够用很久。`对大多数 Agent：Memory = 一个 Markdown 文件 + 一种习惯。` 当记忆数量超过约 200 条、或需要复杂检索（多条件过滤、向量语义检索）时，才值得迁移到数据库方案。

##### 第三条检索路线：keyword search / BM25

已有报告覆盖了两条检索路线——向量语义检索（2.2）和 LLM side-query（3.2）。但业界实践中还有**第三条路**：

> "最新的一些 memory 系统用了 keyword search：记忆存成 markdown → 分片 → 存 BM25 库 → 搜 chunk → 弹 top-k 片段。感觉还是蛮准的。关键字往往是最重要的。如果你 markdown 写得非常好的话，可能 keyword search 的效率更高。"——AI_Julie 视频 07

| 检索路线 | 原理 | 优点 | 缺点 |
|---------|------|------|------|
| 向量语义检索 | embedding → cos 相似度 | 理解语义（"简洁"≈"不啰嗦"） | 不准——"总是搜不到最满意的东西" |
| LLM side-query | LLM 读 name+description 选文件 | 理解力最强 | 每次检索都调 LLM，成本高 |
| **keyword/BM25** | 词频 + 逆文档频率 | Google 验证了几十年、marksown 好则效率极高 | 不理解语义（"简洁"≠"不啰嗦"） |

**三条路不是互斥的**——生产上可以 keyword 粗筛 + 向量精排，或 keyword 快速兜底 + LLM side-query 复杂查询。关键是文件仓库方案天然支持 keyword 检索（markdown 文本），不需要额外建向量索引。

> "似乎 keyword 设计好像比炒作了半天的 semantic 设计好像更见效，很有意思。"——AI_Julie 视频 05

### 3.3 记忆巩固：从情节到语义

Agent 每一天产生大量"情节"（"10:23 用户问了 X，助手回 Y""14:15 用户纠正了偏好 Z"）。但注入上下文的应该是"语义"（"用户偏好 Z"），不是全量情节日志。

**门控巩固（Gated Consolidation）流程**：

```
Episodic Log（情节日志）
  │  "10:23 用户: 帮我写 Python → 14:15 用户: 不要用 class → ..."
  │
  ├── Gate 条件（满足任一触发）：
  │     · 每 20 轮对话
  │     · 每 100 次活动
  │     · 距上次巩固 > 24h
  │
  ▼
Summarizer Agent（摘要 Agent）
  │  "把这批情节中值得长期记住的事实提炼出来"
  │
  ▼
Steal into Facts（写入语义记忆）
  │  "用户偏好：代码不用 class component"
  │  "用户偏好：Python 通信用 httpx 不用 requests"
  │
  ▼
Semantic Memory（向量库）
  └── 检索时优先召回这些"从情节中蒸馏出来的耐久事实"
```

> **核心认知：不要每条新活动都立刻写进语义记忆——等于存两遍。达到阈值再巩固。情节记流水，语义记精华。情节管"发生过什么"，语义管"以后必须知道什么"。**

##### Running Summary 的升级：分段增量摘要

已有报告 2.3 的 Running Summary 是单一 buffer 只增不减，长对话下会退化。视频中的升级方案——**分段 + 打标 + 优先级加载**：

```
不要等到上万 token 再统一压缩 → 设阈值 2K token 就压缩
  → 只压缩当前区间历史，保留多段分段摘要（1-10压缩一段、11-20再压缩一段）
    → 每段打时间戳 + 优先级标记（目标/约束高权重、闲聊低权重）
      → 检索时优先加载高优先级的分段摘要
        → "不会抹平早期的关键信息，大幅度降低了重要信息丢失的概率"
```

**摘要丢信息的四个具体根因**：
1. 摘要统一压缩所有内容、平等对待——核心需求与闲聊一起压
2. 分不清早期核心目标和后期临时闲聊
3. 没有分层存储——偏好和临时会话混在一起压缩
4. 粗颗粒度摘要丢弃细腻约束——**否定类需求（"不要出错"）最容易被吞掉**

> "总体来说感觉就像是你的 system prompt 没有写好。"——AI_Julie 视频 08

##### Observer + Reflector 两次压缩（超长对话方案）

已有报告 3.3 的 Summarizer 是单次压缩。对于超长期高频工具调用，需要**两次压缩**：

```
超长期高频工具调用 → 对话+工具返回海量文本 → 超 token 阈值
  │
  ├── Observer（观测器）：后台异步压缩（不阻塞对话）
  │     · 按 token 触发，不按轮数（"大模型认 token 不认轮数，你有可能一轮就超过 2k"）
  │     · 几十倍压缩，只保留关键事实，丢弃无关内容
  │     · 观测摘要稳定不变 → 支持 prompt 缓存
  │
  └── Reflector（反思器）：对 Observer 输出做二次聚合
        · 优先级评估 + 冲突消解 + 过时标记
        · 消除 Observer 多次压缩产生的新旧重复和矛盾
```

**与单次 Summarizer 的本质差异**：Observer 管"压体积"（信息压缩），Reflector 管"消矛盾"（质量保证）。两次压缩分离关注点，比一次笼统压缩更可靠。

### 3.4 记忆系统的诊断与优化

#### 四大常见病灶

| 病灶 | 症状 | 根因 | 修复方向 |
|------|------|------|---------|
| **记忆膨胀** | 检索越来越慢，top_k 召回噪声增多 | 记忆数量无上限增长 / 每轮原话全量入库不做筛选 | 设 TTL 过期、长期未访问自动清理、限制每用户记忆上限、**写入时不筛选的"全量入库"是检索变差的直接原因** |
| **记忆污染** | Agent 用了错误的偏好/事实 | 错误信息被写入记忆（废话、LLM 推测、失败的工具调用） | 强化 Write 环节的 Noise Filter：只有耐久事实才写，模型废话/失败调用不写 |
| **记忆遗忘** | 重要信息被窗口挤出或摘要丢失 | 窗口太小 / 摘要太激进 / 没有 Working Memory 保护关键信息 | ① Working Memory 前置隔离"绝对不能丢"的信息 ② 增大窗口预算 ③ 摘要分段+优先级标记 |
| **Context Rot** | 上下文越长，模型反而表现越差 | Transformer 架构不保证均匀读完整段输入 | "保持活跃的上下文要小，越尽量空模型才清醒" |

##### Context Rot：为什么更多记忆会让 Agent 更差

> "窗口再大，模型也不会均匀读完整段输入。你输了一些最后的内容，它估计就是忽略掉的，它只读中间或者只读开头。"——AI_Julie 视频 09

完整因果链：
```
更多记忆 → 上下文变长
  → 模型不均匀读（只关注头尾、忽略中间）
    → 研究显示：几千 token 历史下，会话早期的指令遵从率可能掉到 1/3
      → 这是 Transformer 架构先天的缺陷，不是 prompt 问题
        → 修复方向："尽量输入小而精的 context"
          → "memory 系统的价值是在扔掉了多少，而不是存了多少"
```

> 这个数据点（"几千 token 历史下遵从率掉到 1/3"）是面试中解释"context 为什么不能太长"的最佳论据——让"小而精"从口号变成有研究依据的设计原则。

##### 静默失败：最危险的记忆故障模式

> "memory 坏了不报错，agent 只能慢慢变差。你 memory 坏了，等于你脑子也坏了。所以往往要到'自信地忘掉不该忘的事实'时才发现。"——AI_Julie 视频 09

**为什么静默失败比显式报错更危险？**
- 数据库崩溃 → 报 connection error → 立刻发现
- 记忆系统静默退化 → 检索越来越不准、冲突越来越多 → 用户只是觉得"它变蠢了" → 直到某天 Agent 基于错误记忆做了一个自信的错误决策

**防御手段**：自建评测集、定期跑"三问测试"（3.6 节），用指标而非感觉来判断记忆健康度。

> "厂商自测分数当营销看——LongMemEval 强方案在长会话上仍可能掉约 30% 准确率。"——AI_Julie 视频 09

#### 优化优先级

```
1️⃣  先防"遗忘"：Working Memory 隔离硬约束 → 增大窗口 → 优化摘要
      ↓  （关键信息不丢了）
2️⃣  再治"膨胀"：设记忆上限 + TTL 过期 + 清理策略
      ↓  （检索不慢了）
3️⃣  最后修"污染"：强化 Write 噪声过滤 + Reconcile 冲突检测
      ↓  （记忆不自相矛盾了）
```

### 3.5 常见错误与避坑清单

#### 🔧 设计阶段（动手前）

**No.1 把记忆当成"数据库"来设计**
> 每条对话都存一行 → 噪声淹没信号、冲突无法调和、永远不会忘。记忆系统的核心不是"存"，是"决定存什么 + 忘什么 + 冲突时信谁"。设计 Write/Reconcile/Forget 三个环节的优先级远高于选存储后端。

**No.2 上来就上重型 Memory 产品**
> Mem0/Letta/Zep 等产品有价值，但不是默认选择。先问自己"我的 Agent 真的需要跨会话个性化吗？代码库大到摘要扛不住吗？多 Agent 必须共享状态吗？"——三个问题的答案都是"是"才值得上。否则 `CLAUDE.md + Notes 文件 + 摘要` 够用很久。

**No.3 四类记忆只用一种**
> "我用了向量库，应该不需要窗口和摘要了吧？"——错了。向量检索有精度瓶颈，近期精确信息（"你刚才说的第三个方案"）语义检索召回率远不如直接放上下文。三类记忆互补——窗口管精确、摘要管连贯、向量管持久。

#### ⚡ 实现阶段

**No.4 System Prompt 被滑动窗口挤出**
> 滑动窗口的 Pop 不区分消息类型，System Prompt 会被当普通消息从头部挤掉。必须加保护位——system 消息不参与 Pop。

**No.5 Token 编码与模型不匹配**
> tiktoken 的 `cl100k_base` 是 GPT-4 时代的编码，o1/GPT-4o 用 `o200k_base`。用错编码导致"你以为没超限实际超了"。模型切换时必须同步换 encoding。

**No.6 嵌入未归一化就直接用点积算相似度**
> 余弦相似度的分母是 `|A|×|B|`，不做归一化时不能直接用点积替代。SentenceTransformer 设置 `normalize_embeddings=True` 避免这个坑。

**No.7 没有用户隔离**
> 多用户场景下忘记按 user_id 过滤检索结果 → 用户 A 的记忆被用户 B 的查询召回。隐私问题 + 准确性灾难。

#### 📣 呈现阶段

**No.8 面试中只讲"用了向量库做记忆"**
> 这是 60 分回答。面试官期待的 88 分回答是："我设计了 Write/Read/Reconcile/Forget 的完整闭环——Write 环节有噪声过滤只存耐久事实，Reconcile 用 Last-Write-Wins 解决冲突，Forget 用 TTL+长期未访问清理防止膨胀。"讲的是**设计决策**而不是"用了什么库"。

**No.9 忽略 Memory 安全风险**
> 持久记忆 = 持久攻击面。如果 Agent 读到恶意的内容（毒 README/邮件），把它当"事实"写入长期记忆 → 几天后另一个高权限会话召回并执行。持久记忆把一次性漏洞变成了潜伏 Agent。面试中能提到这一点是高分信号。

**记忆投毒的完整路径**（来源：AI_Julie 视频 09）：
```
毒内容（毒 README / 邮件 / 网页）
  → 被 Agent 当作有用信息读入 working memory
    → Write 环节未识别为恶意内容，写入长期记忆
      → 几天后，另一个会话检索到此"记忆"并全量加载到 context
        → 高权限场景下被召回执行
          → 持久记忆把一次性漏洞变成了潜伏 Agent
```
防御方向：写入前增加**可信度评分**（来源可信度、内容一致性校验）、关键操作前**人工确认**。

**No.10 全量入库不做筛选 → 检索越来越不准**
> "每轮结果都入库 → 向量库越来越庞大 → 你的检索越来越不准。"（AI_Julie 视频 07）"你把所有的东西都记住了之后，发现你什么都记不住了，所以选择性地遗忘一些东西吧。"写入时不筛选 = 检索质量随时间单调下降。修复：Write 环节必须带噪声过滤，不是每句话都值得长期记住。

**No.11 Working Memory 更新时叠加而非替换 → 幻觉的来源是你自己**
> "昨天的人设跟今天的人设不一样，昨天的人设没删，模型不知道你到底是哪个人设。感觉不像是模型的幻觉，还是你自己的一个保存的东西信息有毛病。"（AI_Julie 视频 08）Working Memory 字段更新必须是替换操作，不能追加。旧值+新值并存 = 模型看到两个矛盾的自己 = 随机选一个 = 幻觉。

**No.12 摘要不做分段，一次性全量压缩长历史**
> 当对话超过几千 token 时，一次性全局摘要必然丢失信息——特别是"不要出错"这类否定约束和早期核心目标。修复：设阈值分段压缩、打时间戳、检索时优先加载高优先级段（详见 3.3 分段增量摘要）。

### 3.6 记忆评测

记忆评测是业界开放问题。目前没有像 RAGAS 那样成熟的标准化框架，但可以从三个维度自建评估：

#### 评测三维度

| 维度 | 测什么 | 怎么测 |
|------|--------|--------|
| **Reconcile 准确性** | 偏好更新后旧值是否被覆盖？ | 三问测试：①稳定偏好应记住 ②已变更事实应覆盖旧值 ③从未告知的信息应拒绝瞎编 |
| **检索命中率** | 当前 query 需要的记忆是否被召回？ | 准备 20 条标注数据集：query → 期望召回的记忆 ID 列表 |
| **遗忘控制** | 重要信息是否被错误遗忘？噪声是否被正确遗忘？ | 长期运行后审计：检查过时/错误记忆是否被 TTL 或清理策略移除 |

#### 业界基准（了解即可）

- **LongMemEval**：长程多会话记忆评估基准。当前最强方案在长期多会话场景仍可能掉 ~30% 准确率——说明记忆评测本身仍是开放问题。
- **Memory 投毒研究**：普通消息植入成功率可 >90%。评测记忆系统的安全边界同样重要。

> **实操建议**：先写 5 个测试问题再上系统。测不过 = 只有"存"没有"调和"。不要等上线后才发现记忆系统在静默失败——记忆系统坏的时候不会报错，只会悄悄地给出错误的上下文。

### 📋 面试卡片：工程层

**Q1：Agent 记忆系统和数据库有什么区别？**

A：数据库是被动的——你存什么它记什么。记忆系统是主动的——它决定**该不该存**（Write 过滤）、**新旧冲突信谁**（Reconcile）、**什么时候该忘**（Forget TTL）、**当前该想起来什么**（Retrieve + Rank）。把记忆当成数据库用有三个致命后果：噪声积累（废话也存）、事实冲突（用户周一和周三说法矛盾，两条都躺在库里，检索随机召回）、永远不遗忘（过时信息永远占位）。

**Q2：Write 环节为什么需要噪声过滤？怎么实现？**

A：对话中 90% 的内容不值得长期记住——模型废话、半截推理、失败的工具调用、闲聊。写进去就是污染检索。实现：① LLM 提取 Prompt 中明确要求"只提取耐久事实，无内容输出 NONE"② 失败的工具调用/错误消息不触发提取③ 只写"以后还需要知道"的信息，不写"这次对话才需要"的临时上下文。

**Q3：Reconcile 的五种策略中，为什么 Last-Write-Wins 是默认首选？**

A：因为简单且符合直觉——用户最近说的话通常代表最新偏好。90% 的记忆冲突场景都是"用户改主意了"，Last-Write-Wins 直接覆盖最合理。但 10% 的高风险场景（如权限变更、金融信息、医疗偏好）不应该静默覆盖，应该升级给用户确认（冲突升级策略）。

**Q4：文件仓库 + 索引方案和向量数据库方案怎么选？**

A：文件方案适合记忆数量 < 200 条、查询靠 LLM side-query 或关键词的场景——优势是极简、可 git 版本控制、人类直接可读。向量库方案适合记忆数量 > 200 条、需要语义检索的场景——优势是语义理解、规模化。**判断标准不是技术偏好，是记忆数量级和检索需求。对大多数个人 Agent，文件方案够用很久。**

**Q5：记忆巩固（Episodic → Semantic）为什么不能每条新活动都立刻写进语义记忆？**

A：两个原因。① 成本：每次写入需要 embedding 计算，频繁写入浪费资源。② 质量：情节中有大量一次性的、不具长期价值的信息。先积累一批情节 → 达到阈值（如 20 轮）→ Summarizer 提炼耐久事实 → 一次性写入语义记忆——这样写进去的都是"蒸馏过的精华"，不是流水账。门控的频率是"省成本"和"保新鲜度"的 trade-off。

**Q6：怎么评估一个记忆系统好不好？**

A：三个维度自建评测。① Reconcile 准确性——三问测试（稳定偏好应记住/变更事实应覆盖/从不知道的应拒绝瞎编）。② 检索命中率——准备 20 条标注数据（query→期望召回的记忆 ID），计算 recall@k。③ 遗忘控制——长期运行后审计，检查过时记忆是否被正确清理、重要记忆是否被误删。目前没有像 RAGAS 那样的成熟标准框架，记忆评测是开放问题——这意味着你在面试中提到"我自建了三问测试"本身就是区分度。

**Q7：Context rot 是什么？怎么解释给面试官听？**

A："Context rot = 上下文越长，模型的注意力越不均匀。Transformer 架构不保证均匀读完整段输入——你输了一大堆内容，它可能只认真地读头尾，中间区域随意扫描。研究显示，几千 token 的历史下，会话早期的指令遵从率可能掉到 1/3。所以 memory 系统的价值不是能存多少——而是扔掉了多少。保持活跃上下文小而精，模型才清醒。"面试官追问修复方向 → "① 检索排序只注 top-k（不是越多越好）② 摘要管长历史、不拼全量原文 ③ Context rot 是 transformer 先天的缺陷，不要把修复希望寄托在'更大窗口'上。"

**Q8：记忆投毒（memory poisoning）的路径是什么？怎么防？**

A：路径——毒内容（恶意 README/邮件/网页）被 Agent 读入 → Write 环节未识别 → 写入长期记忆 → 数天后另一高权限会话检索召回并全量加载到 context → 持久记忆把一次性漏洞变成了潜伏 Agent。防御方向：① 写入前加可信度评分（来源可信度、与已有事实的一致性校验）② 关键操作前人工确认 ③ 定期审计长期记忆中的高敏感条目。面试中能独立讲清这个攻击路径是高分信号——大多数候选人只关注 memory "怎么存"，没人想"存错了怎么办"。

**Q9：Agent 系统的三维评估指标是什么？跟单纯的记忆评测什么关系？**

A：三维——完成度（LLM-as-judge 判断任务是否完成，注意 agent 自报"完成了"不可信，必须有 trace 做判断依据）、Token 成本（每轮花了多少 token 多少钱，"你可以告诉用户到底要花多少钱"）、Latency（延迟+错误率）。记忆评测是这三维里"完成度"的支撑——检索命中率低 → 上下文缺少关键信息 → 任务完成度下降。三维评估告诉你"Agent 好不好"，记忆评测告诉你"为什么好/不好"。闭环：设标准 → 不达标 → 回溯优化 memory 和 loop。

> "Agent 记忆是三层次互补体系——短期窗口管对话连贯性、中期摘要压缩长历史、长期向量库管跨会话画像。但记忆系统最难的不是怎么存，而是决定存什么（Write 过滤）、新旧冲突信谁（Reconcile 五种策略）、什么时候该忘（Forget TTL）。好的记忆系统靠'故意忘掉什么'来运转，不靠存得更多。"

---

> **一句话总结：Agent 记忆不是数据库——它是一个决定"记住什么、忘掉什么、什么时候想起来"的持续决策系统。**
